# Портирование на 64 бита (LP64)

Движок восстановлен из 32-битного `PILOTS.EXE` и весь написан под 32-битные указатели: в оригинале они умещаются в `int` и обратно. На LP64 это ломается четырьмя разными способами, и для трёх из них принято решение **не переписывать код, а нарушить предпосылку оригинала** — положить пул памяти ниже 2 ГБ. Здесь зафиксировано, что именно проверено, чем инвариант гарантируется и, главное, **какие ошибки он не покрывает**.

## Корень: указатели, умещённые в int

Самый показательный пример — сигнатура диспетчера опкодов:

```c
char __stdcall GameOpcodeDispatcher(int opcodeData, int dataOffset, int arrayIdx,
                                    int subIdx, int slotIdx, int opcodeType);
```

(`pilots_globals.h:127`) — первый аргумент объявлен как `int`, и вызывающая сторона честно туда усекает (`gameloop.c:579`):

```c
GameOpcodeDispatcher((int)g_TemplateDataBuffer, ...)
```

а сам диспетчер разворачивает обратно (`gameloop.c:336`, `gameloop.c:338`):

```c
g_GameLoopDataPtr = (GameLoopData *)(INT_PTR)opcodeData;
*(_BYTE *)(INT_PTR)(opcodeData + 1) = g_DefaultFrameRate;
```

На x86 круговой «указатель → int → указатель» потерь не даёт: указатель целиком 4 байта. На LP64 `(int)` отбрасывает старшую половину, а `(INT_PTR)` **знаково расширяет** младшую — то есть результат корректен **только если исходный адрес меньше 2 ГБ** (бит 31 должен быть нулевым). Иначе получается `0xFFFFFFFF_…`, и первый же опкод, трогающий свои данные, падает.

## Откуда берутся все игровые указатели

Все они указывают в **один** блок `GlobalAlloc`, а не в статические массивы:

1. `resource.c:402` вызывает `InitializeVideoSystem(..., (struct VideoDataBuffer *)&g_MemoryPool)`;
2. `graphics.c:87`–`88` — `hGlobalMem = GlobalAlloc(2u, a3->field_0); pLockedMem = GlobalLock(hGlobalMem);`
3. `graphics.c:92` — `a3->field_4 = (INT_PTR)pLockedMem`, а `field_4` смещением +4 (при `#pragma pack(2)`) и есть `poolBasePtr` (`pilots_types.h:141`).

Из этого блока раздаётся всё: `g_TemplateDataBuffer`, `g_SpriteSlotArray`, `g_AnimationSlotArray`, `g_TileMapBuffer`, `g_ScreenSnapshotArray` (`resource.c:411`–`466`), буферы видео (`video.c:86`–`114`), снапшоты (`resource.c:304`, `saveload.c:272`).

## Принятое решение: инвариант вместо переписывания ~240 мест

Коммит `cd61a09` сознательно отказался править ~240 усекающих `(INT_PTR)`-мест и вместо этого гарантирует, что обрезанный указатель всегда восстанавливается корректно — «spares rewriting ~240 (INT_PTR) call sites».

**Linux / aarch64 — принудительно.** `win32_shim.c:588` (`Shim_AllocLow`) кладёт каждый блок `GlobalAlloc` в первые 2 ГБ: `MAP_32BIT` есть не везде, поэтому для aarch64 — запрос по hint-адресу `0x10000000`, после чего блок **отвергается**, если он выше (`win32_shim.c:605`):

```c
if ( (UINT_PTR)p > 0x7FFFFFFFu ) { munmap(p, total); return 0; }  /* too high: the int round trip would not survive it */
```

Переопределённые `GlobalAlloc`/`GlobalFree` (`win32_shim.c:613`, `:627`) лежат внутри `#ifndef _WIN32` (`win32_shim.c:35` … `:1438`).

**Windows x64 — не нормируется, только наблюдается.** `GlobalAlloc` там настоящий, код ограничение адреса не накладывает. Однако инвариант «< 2 ГБ» обязателен и там, и он **уже доказан самой работой игры**: при адресе ≥ 2 ГБ `(INT_PTR)opcodeData` на `gameloop.c:336` дал бы `0xFFFFFFFF_…`, и игра упала бы на первом же опкоде 0x92 в первой сцене. Примечательно, что проверить это по логу нельзя — `graphics.c:89` печатает `pLockedMem` уже усечённым (`(unsigned int)(INT_PTR)`), старшую половину увидеть негде.

## Четыре семейства LP64-ошибок

Инвариант «< 2 ГБ» спасает **усечения**. Он **не спасает** ошибки ширины — те правятся в коде.

| # | Семейство | Спасает инвариант? | Пример и статус |
|---|-----------|--------------------|-----------------|
| 1 | Усечение + знаковое расширение `(INT_PTR)` | **да** | `gameloop.c:336`, `:338`; `resource.c:411`, `:439`, `:453`; `video.c:86`–`114`; `memory.c:118`. ~240 мест, не трогаются. |
| 2 | Выбор **байта** указателя `HIBYTE`/`BYTE2` | **нет** | `HIBYTE` берёт байт `sizeof(ptr)-1`: 3 на x86, 7 на LP64. Исправлено на `BYTE3` в `render.c:261` (коммит `c36819d`) — `BYTE3` читает байт 3 на обеих архитектурах. |
| 3 | Запись **половины** указателя `*(_DWORD*)&ptr = 0` | **нет** | На LP64 не обнуляет старшую половину — в поле остаётся мусор. Исправлено на `*(INT_PTR*)&… = 0` в `render.c:265` и `gameloop.c:697` (оба — `c36819d`). |
| 4 | 32-битная **арифметика** поверх указателя | **да** | `*(_DWORD *)&object->spriteDataPtr += 8` / `-= 8 * v3 - 8` в `animation.c:234`, `animation.c:242` и `render.c:750`, `render.c:756`. Разбор ниже. |

### Почему семейство 4 чинить не нужно

`*(_DWORD *)&ptr` на LP64 читает и пишет только младшие 32 бита, старшая половина остаётся нетронутой. Разберём обе операции.

`+= 8` даёт верный результат, если `low32 + 8` не переполняет 32 бита, то есть при `low32 ≤ 0xFFFFFFF7`. Инвариант даёт `low32 < 2 ГБ` — запас более чем двукратный.

`-= 8 * v3 - 8` — это откат после проигрыша кадров: указатель стартует с `P`, после `v3 - 1` шагов стоит на `P + 8*(v3-1)`, и вычитание возвращает его ровно в `P` (индекс кадра при этом сбрасывается в 0, `animation.c:241`–`242`). Пока переполнения при `+=` не было, занимание невозможно: `low32 = low32(P) + 8*(v3-1) ≥ 8*(v3-1)`.

**Единственный режим отказа — таблица кадров пересекает границу 4 ГБ.** Инвариант «< 2 ГБ» это исключает.

Отсюда следует и то, что править эти четыре места **не нужно**: `cd61a09` специально выбрал инвариант вместо переписывания, а починка 4 мест из ~240 однотипных создала бы ложное впечатление, что остальные сломаны.

## За рамками инварианта

Эти места не покрываются «< 2 ГБ» и требуют отдельного разбора:

- `audio.c:676` — `g_hMainWindow[0] = (DWORD_PTR)g_MainWindow`: HWND усечён до 32 бит. Это безопасно, но по **контракту Windows**, а не по инварианту: в 64-битных Windows хэндлы окон гарантированно помещаются в 32 бита (иначе не работал бы весь Win32 API).
- `audio.c:725`–`726` → `audio.c:806` — поле объявлено как `int[]` внутри побайтово-точной автогенерированной `game_globals_struct.h`, усечение и обратное знаковое расширение. Ширину поля на месте не увеличить, нужна боковая таблица. Подробности — в [sound-disappears.md](sound-disappears.md).
- `memory.c:98` — `v1 += *v1 & 0x7FFFFFFF`: в порте уже добавлена маска перед 64-битным сложением, потому что флаг занятости блока лежит в бите 31 заголовка.

## Правило для будущих правок

Прежде чем «чинить» усечение указателя на LP64, проверьте, какое именно семейство перед вами:

- **усечение и обратное знаковое расширение** — уже покрыто инвариантом пула, код не трогать;
- **выбор байта или запись половины** — инвариант не помогает, нужна явная правка ширины (семейства 2 и 3);
- **поле указателя в `game_globals_struct.h`** — править нельзя, файл автогенерированный и должен совпадать с оригиналом байт в байт; решение всегда снаружи структуры.

Проверить инвариант на Linux можно сборкой в контейнере: если `Shim_AllocLow` вернул 0, блок не помещается в 2 ГБ и запускать игру смысла нет — она упадёт на первом опкоде, тронувшем данные пула.
