# План миграции SDL2-порта на перестроенный main — план и исполнение

Живой трекер: здесь план фаз и его исполнение. Анализ кодовой базы (секции A–J) —
в соседнем `migration-plan.md`. Ветка `port-main`; референс — ветка `sdl2` с тэгом `v0.1`.

## План фаз

- **P0** — ветка `port-main` от `main`, инфраструктура (`tests/`, `third_party`, `.gitignore`, `AGENTS.md`), разведка архитектуры — **выполнено**.
- **P1** — SDL2 на Windows x86: окно/презент/ввод через SDL на основе `host.c`, восстановление `debug_log.h` и дебаг-маркеров, сборка с SDL2, окно 640×480. MCI-видео и winmm-звук остаются как есть — **выполнено**.
- **P2** — LP64/x64: снятие 32-битных `_Static_assert`, pointer-as-int, x64-сборка — **выполнено**.
- **P3** — Linux (CMake, win32_shim/mci_ffmpeg, SDL-аудио) — **выполнено**.
- **P4** — Switch (`switch_libnx`, пад, low-memory) — **выполнено** (сборка `.nro` зелёная на всех конфигурациях; запуск на консоли — когда она проснётся).
- **P5** — фичи порта по одной с харнессами (fullscreen/stretch, hotspots, cursor keepalive, movie sound, libADLMIDI MIDI, `-datapath`, load-индикатор, профиль лупы, coalescing, стик-курсор) — **в работе**: выполнены **fullscreen/stretch + `-datapath`** (`b2a54fe`; `tests/linux/fullscreen.sh` 13/13, `datapath.sh` 22/22), **movie sound** (`7f8d1d3`; `movieaudio.sh` 9/9), **hotspots** (`6044869`; `hotspots.sh` PASSED — харнесс адаптирован: AVI ищутся рядом с exe, харнесс ждёт второй `PlayAvi: end`), **cursor keepalive** (`903fd62`; только сборка — фича Switch-only, без харнесса, верификация на консоли, когда проснётся). В коде уже с P3/P4: coalescing, троттлинг стика, вызов `SdlBackendLoadBeat` из `_read` (тело индикатора — нет). Осталось: **libADLMIDI**, **load-индикатор**, **профиль лупы**.
- **P6** — полная матрица тестов зелёная (Windows x86/x64, Linux, Switch).

## Исполнение

### P1 (выполнен)

Шов собран в `SRC/sdl_backend.c` (только SDL) и точечных правках `host.c`:

- **Окно**: `Host_CreateWindow` вызывает `SdlBackendCreateWindow` (SDL создаёт окно, `SDL_GetWindowWMInfo` → HWND, subclass через `SetWindowLongPtr(GWLP_WNDPROC)` с сохранением `s_OrigWndProc`). Подкласс `SdlGameWndProc` отдаёт игровой набор сообщений (клавиатура/мышь/палитра/`WM_PAINT`/`WM_SIZE`/`WM_GETMINMAXINFO`/`MM_WOM_DONE`/`MM_MCINOTIFY`/close) в неизменённый `Host_MainWndProc`, остальное — `CallWindowProc(orig)` SDL. `g_MainWindow` = этот HWND, поэтому MCI/waveOut работают как есть. Окно 640×480 (флаг `SDL_WINDOW_RESIZABLE` по `header->resizable`).
- **Презент**: DIB-секция не создаётся (`Host_InitVideo`), кадровый буфер из арены (`GmFrame_Init`). `Host_BlitRect` → `SdlBackendPresentRect` (8-битный bottom-up прямоугольник через палитруный LUT → теневой ARGB, без показа), `Host_Flush` → `SdlBackendFlushPresent` (один `SDL_UpdateTexture`+`RenderCopy`+`RenderPresent`, только если кадр «грязный»). Растворение (dissolve) сводится к одному кадру — принятое отклонение.
- **Палитра**: `Host_SetPalette` → `SdlBackendUpdatePalette` (LUT без R/B-свопа) + `SdlBackendClearBlack`/`SdlBackendDrawGrid` вместо GDI-заливки чёрным/сеткой. GDI-палитра создаётся по-прежнему (нужна AVI-путям), `SetDIBColorTable`-блок пропускается сам (`g_hDibDC` NULL).
- **Ввод**: SDL-события просто дренируются (`SdlBackendPumpEvents` в главном цикле); реальный игровой ввод идёт Win32-сообщениями через подкласс (как в оригинале).
- **Диагностика**: `debug_log.h` перенесён с `sdl2` (добавлены `#include <string.h>` и `#pragma warning(disable:4505)` для `/W4 /WX`), лог-глобалы — в `data.c` под `#ifdef _DEBUG`, `#include "debug_log.h"` — в `gm.h`. Маркеры: окно (размеры), `SetPalette` (count/grid), первый present, `PlayAvi` start/end, `GmGame_Initialize` ok, `click L` (ввод), `ENTER: WinMain`/`GameMainLoop`.
- **Билд**: `build-vs2022.bat` **и** `build.bat` синхронно получили `/external:W0 /external:I "%SDL2%\include"`, линковку `SDL2.lib` и копию `SDL2.dll` в `out\`. Обе конфигурации (debug и release) собираются чисто под `/W4 /WX`.

Проверено запуском (debug и release): окно 640×480, картинка уровня через SDL в полном цвете, курсор рисуется движком при вводе, `click L: …` доходит до `Host_MainWndProc`, клик по кнопке нижней панели перезагружает палитру (переход экрана), ноль `EXCEPTION`. AVI-интро и start-фильм воспроизводятся через MCI (см. ниже).

**MCI-видео (закрыто).** Раньше AVI не проверялось (тест шёл без `MOVIES`). С каталогом `MOVIES` рядом с exe найден и исправлен дефект шва: окно AVI-ребёнка создавалось 0×0. Причина — окно показывалось `ShowWindow(SW_SHOWNORMAL)` только для интро (`name=NULL`), а в оригинале окно создавалось скрытым, так что переход hidden→visible давал первый `WM_PAINT`, которым `Host_AviWndProc` впервые мчит `AVIWnd32` из 0×0 в реальный размер. SDL-шов создавал окно уже видимым → `ShowWindow` был no-op → `WM_PAINT` не было → 0×0 → чёрный экран. Именованные AVI (start/final) полагались на `InvalidateRect` и были неуязвимы. Исправление: `SDL_WINDOW_HIDDEN` в `SdlBackendCreateWindow`. Проверено: `AVIWnd32` = 320×240, кадр интро рисуется, интро доигрывает до конца (`PlayAvi: end playing=0 quit=0` — `MM_MCINOTIFY` гасит модальный цикл без зависания, обрезка `dwCallback` безвредна на x86 через fallback на родителя), затем `GameMainLoop` и start-фильм.

Замечание: главный цикл считает `cursorInWindow` по реальному положению курсора (`GetCursorPos`+`ScreenToClient`), поэтому опубликованный (`PostMessage`) клик обрабатывается, только если реальный курсор зажат над окном — это логика игры, а не шва.

### P2 (выполнен): план

**Что ломается на LP64 (по разведке):**

1. `gm.h:20` `_Static_assert(sizeof(void*)==4)` и ~47 layout-ассертов структур. Сборка идёт с `/std:c17`, так что ассерты активны (в legacy-режиме MSVC `_Static_assert` вообще не парсится — поэтому у `sdl2` свои бата без `/std` и гм-файлы не компилируют).
2. **VM усекает адреса в `int32`**: `lo = (int32_t)(intptr_t)(globals|objectVars|sp + operand)`, `Push(&sp, (int32_t)(intptr_t)ip)` (vm.c:172-243), стек-слоты — int32. Усечение знаковое: выживает только память **ниже 2 ГБ** (не 4).
3. Источники памяти сейчас **высокие**: арена — `GlobalAlloc(GMEM_MOVEABLE)` (host.c:875, эмпирически на x64-Windows отдаёт `0x1E1…`), GmHeap ходит по арене (одна точка лечит оба), статические массивы (`g_Vars` и пр.) и стек VM (`s_vmStack`) — в `.bss` при базе x64-образа по умолчанию `0x140000000` (тоже высоко).
4. **Сериализация пула**: `GM_POOL_ENTRY` = union `words[4]` (16 байт), в него входят `GM_SPRITE.frame`/`GM_OBJECT.vars` (4-байтовые указатели в последних 4 байтах). Save пишет блок raw с rebase кадров в смещения от арены (save.c:340-343). На LP64 указатели вырастут до 8 байт, union до 24 → формат разъедется. `words[]` у пула в коде не эксплуатируется (2 хита — rule-union в `load.c:407/411`).
5. `load.c` копирует записи файла в структуры raw-`memcpy` (`GmLoad_CopyRecord`) — у структур с указателями «в середине» layout на LP64 сдвинется; аудит целей CopyRecord.

**Решения:**

- **Низкая память (< 2 ГБ)** — как `Shim_AllocLow` референса: (а) выделение арены через VirtualAlloc с hint'ом ниже 2 ГБ вместо `GlobalAlloc`; (б) пиннинг базы x64-образа (`/BASE` ниже 2 ГБ + `/DYNAMICBASE:NO`, у референса база уже пиннена) — тогда все статические массивы и `s_vmStack` низкие, и **весь int32-адресный модель VM остаётся без изменений** (это и есть суть «избежать переписывания сотен точек усечения»).
- **Рантайм-структуры** (`GM_ARENA`, `GM_CLASS`, `GM_SOUND`, `GM_PANEL`, `GM_DIRTY_RECT`…) растут до native-указателей; их ассерты — условные по архитектуре.
- **Формат**: `GM_POOL_ENTRY` в сохранении остаётся ровно 16 байт с 32-битным слотом кадра — save/load конвертируют запись явно (поля → формат-16-байт → файл и обратно), вместо raw-записи растущего union. `.SAV` байтово совместим между x86 и x64 (проверка — взаимная загрузка).
- Аудит `GmLoad_CopyRecord`-целей; там, где форматная запись упирается в указатель — конвертация на границе.
- `natives.c`/`vm.c`: без изменений при низкой памяти.

**Шаги:** ① пробная x64-сборка → точный список ошибок ② низкое выделение арены + пиннинг образа ③ ассерты рантайм-структур ④ конвертация сохранений ⑤ аудит CopyRecord ⑥ прогон: интро, уровень, save/load round-trip, сверка `.SAV` x86↔x64.

**Выполнено (шаги ①–⑤, прогон до карты уровней):** x64-сборка (`build-vs2022.bat [debug] x64`, образ пинится `/BASE:0x10000000 /DYNAMICBASE:NO`), арена ниже 2 ГБ, `GM_ASSERT_RUNTIME` для рантайм-структур, форматные юниты — 4-байтовые слоты (`GM_FRAME.image`, `GM_RULE_ITEM.script`, таблицы правил/кадров через `GM_RULES_AT`/`GM_FRAME_IMAGE`), сохранения — конвертация `GmSave_Compress/ExpandPoolEntries` (формат 16 байт/запись на обеих архитектурах). Два LP64-бага найдены и починены:

1. **Скрипты создания классов были пусты** (на карте не спавнились флажки уровней): фикстапы `CREATE_SCRIPT` в потоке идут **до** тела класса, а LP64-ветка `GMREC_CLASS` делала `memset` всей структуры — затирая записанные указатели. Запись класса в файле — 4 скалярных байта (`g_RecordSize`), указатели копировать нечем: тело копирует ровно префикс, как и на x86.
2. **Музыка после видео уходила в тишину**: `GmAudio_Restart` → `GmMidi_Open` сбрасывал `g_MidiVolume = 1` (ноты уходили со скоростью 1 из 127). В оригинале громкость жила в устройстве и переживала Close/Open — здесь исходная громкость теперь `FULL_VOLUME`, как и заявлено дизайном `GmMidi_GetVolume`.

Проверено: x64 и x86 debug-прогон (интро → старт-экран → START.AVI → карта) — карта с 12 флажками пиксель-в-пиксель одинакова на обеих архитектурах, музыка звучит с первой ноты в полной громкости, ноль `EXCEPTION: 0xC000`.

**Round-trip `.SAV` x86↔x64 — закрыт (третий LP64-баг):** кросс-загрузка x86-файла на x64 падала `EXCEPTION: 0xC0000005` на мусорном `frame->image`. Корень: layout арены на LP64 был шире — массивы `GmLoad_WorldHeader` отводились `sizeof()` рантайм-структур с указателями (`GM_ROOM`/`GM_CLASS`/`GM_CLASS_SET` 32/16, `GM_GRAPHIC` 16/8 из-за сырого указателя в `GM_FRAME_LISTS`, `GM_SOUND`/`GM_PANEL` 16/8, резерв музыки `sizeof(GM_MUSIC_DATA*)` 8/4) — суммарный сдвиг +0xA00 в мире эпизода; а слоты в `.SAV` считаются от `g_Arena.freePtr`, то есть арена-layout — часть де-факто формата файла, а `GM_ASSERT_RUNTIME` на LP64 молчал. Лечение: эти структуры переведены на фиксированные 4-байтовые слоты (адреса образа/арены ниже 2 ГБ), размеры их фиксирует безусловный `GM_ASSERT_FIXED`; x86-раскладка не изменилась (размеры совпадают). Замеры: новый x86-файл против доизмененного — 6 байтовых диффов, все тайминги (frameCount, тайлы, кадры анимации); x86 vs x64 — 5 диффов, слоты совпадают (единственный дифф слота — байт одного кадра анимации); x64 загружает x86-сохранение и x86 — своё: уровень «Зоопарк» восстанавливается, процесс жив, лог чист.
