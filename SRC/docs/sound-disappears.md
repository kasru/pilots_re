# Пропадают звуковые эффекты (музыка играет) — расследование от 13.10.2026

Статус: **причина не названа, отложено до свежего лога.** Здесь — что уже
отброшено с доказательствами, какая механика осталась и почему текущий лог не
может её подтвердить. Не перепроверяйте отброшенное заново — идите по
чек-листу в конце.

## Симптом

Сообщение пользователя (x64-сборка, `PILOT_RV_x64.EXE`):

- звуковые эффекты пропадают «в начале сцены», на 13-м уровне и на 3-й сцене;
- катсцена в начале сцены — **внутриигровая анимация**, не AVI;
- игрок **ждёт катсцену до конца**, ничего не нажимает;
- музыка при этом продолжает играть;
- после перезапуска звук появляется снова;
- проблема плавающая.

## Отброшено (и чем именно доказано)

| Гипотеза | Почему отброшена |

| Пауза wave-устройства после катсцены | `SdlWave_Pause` — 0 вызовов во всей сессии. И путь **мёртв в принципе**: `PauseWavePlayback()` вызывается только из `video.c:309`, а `ProcessVideoCommands` недостижим — см. ниже |
| Залипший `g_RenderingInProgress` / `g_SoundEnabledFlag` | `TriggerSoundSlot: … muted (…)` — 0 строк; сами вызовы идут без `muted` |

| Закрытие wave-устройства без переоткрытия | `ShutdownMultimedia` вызывался только на 5060 (старт) и 30062 (выход) |
| Исключения | `EXCEPTION` — только строка установки фильтра (1) |
| MCI-ролики (`Native_PlayVideo`) | у пользователя катсцена внутриигровая; MCI-путь к wave-устройству отношения не имеет |
| x64-сдвиг mix-буфера | `g_hMainWindow` — это `int[4096]` (`game_globals_struct.h:271`), поэтому `g_hMainWindow[512*result]` (`audio.c:797`) = сдвиг 2048 байт = `WAVE_BUF_BYTES` — совпадает на обеих архитектурах |

### Почему `ProcessVideoCommands` недостижим

- `dword_416338` (таблица смещений внутриигровых роликов, `+0x62C4`)
  **нигде не записывается как указатель**: инициализируется нулём
  (`game_globals_init.h:775`), и далее только *через* него пишется
  (`gameloop.c:528`) и читается (`video.c:403`). Вызов `ExecuteVideoPlayback`
  читал бы `*(DWORD*)0`.
- Запасной вход `CheckGameState()` (`saveload.c:376`) требует
  `g_DisplayMode[1] == 1`, а `g_DisplayMode[1]` = `HIBYTE(pConfigEx->field_24)`,
  и в логе видно `HIBYTE(field_24)=2`.

Соответственно `SdlWave_Pause` / `SdlWave_Pause: 0` в логах отсутствуют не
потому, что катсцен не было, а потому что этот код не исполняется.

## Оставшаяся механика (не подтверждена)

Единственное объяснение, подходящее под все четыре признака симптома
(эффекты мертвы / музыка живёт / рестарт лечит / плавающая):

`PlaySoundEffect` (`audio.c:730-748`) при `a1 >= 0` и `g_GraphicsState1 != 0`
**выходит, не вызывая `MixAudioBuffers`**:

```c
if ( g_GraphicsState1 ) v7 = 0; else v7 = 2;
if ( v7 == 2 )      MixAudioBuffers();
else if ( v7 != 1 ) return 1;      /* v7==0 → выход без микширования */
```

При этом:

- `g_GraphicsState1` присваивается **только** внутри микшера
  (`audio.c:822: g_GraphicsState1 = v0`) и обнуляет его **только**
  `InitGraphics` (`audio.c:686`), то есть старт/рестарт;
- слот освобождается (`*v3 = 0`, `audio.c:814`) тоже только в микшере;
- `MixAudioBuffers` извне зовётся лишь из `SdlWavePump`
  (`sdl_backend.c:1345`, `:1406` — на каждом `SdlBackendPumpEvents`);
- `SdlWavePump` вызывает микшер **только внутри цикла отчёта о завершении
  буферов**, а тот крутится лишь пока растёт `limit = consumed / 2048`,
  то есть пока `SDL_GetQueuedAudioSize` уменьшается.

⇒ Если открытое непаузированное устройство перестаёт дренировать очередь
(`avail == total` → `consumed = 0` → `limit = 0` → цикл не выполняется ни
разу), то `s_WaveIfCount` застревает, слот не освобождается,
`g_GraphicsState1` остаётся > 0 навсегда, и **все дальнейшие эффекты молчат**
до `InitGraphics`, то есть до перезапуска. МIDI живёт — это другое устройство.

Что осталось невыясненным: почему открытое непаузированное устройство могло
перестать дренировать. Пауза (`SdlWave_Pause`, `sdl_backend.c:1574`) и закрытие
(`SdlWave_Close`, `sdl_backend.c:1491`) в логе отсутствуют.

## Диагностическая дыра (главный итог)

Текущие диагностики не могут ни подтвердить, ни опровергнуть механику выше:

1. **`SdlWave_Queue` зациклен троттлингом** — `sdl_backend.c`, условие
   `s_WaveQueueCalls < 8 || (s_WaveQueueCalls & 63) == 0`: видны только
   звонки `#0..#7` и далее каждый 64-й. В сессии пользователя поздние
   триггеры (26185, 26266) — это вызовы `#8`/`#9`, они **невидимы**.
2. **Все одноразовые логи уже сработали в начале сессии** и повторно не
   напечатаются: `WriteWaveBuffer: first buffer queued to SDL`,
   `SdlWavePump: first completion reported, refill works`,
   `SdlWave_Clear` (`s_WaveFirstClearLogged`).
3. **`SdlWave_Close` и `CleanupWaveOut` вообще не логируются**, поэтому
   незаметное закрытие устройства доказать по логу нельзя (в этой сессии его
   отсутствие удалось вывести только из отсутствия `ShutdownMultimedia`).

Как читать лог, если он появится:

- `TriggerSoundSlot: slot=N` **без** `muted` + **отсутствие** `SdlWave_Queue`
  рядом → кандидат на механику выше, но **нельзя** доверять при
  `s_WaveQueueCalls >= 8` — троттлинг;
- `SdlWave_Queue: … stillQueued=…` с застывшим значением при растущем числе
  звонков → устройство не дренирует, это и есть предпосылка;
- `SdlWave_Pause: 1` без парного `: 0` → другая, уже отброшенная механика;
- `SdlWave_Open: SDL_OpenAudioDevice failed` / `device gave … refusing` →
  устройство не открылось, `InitDirectDraw_Win95` это маскирует (см. ниже).

## Отдельно: латентный x64-баг указателя (не эта проблема, но найден)

`audio.c:725-726` усекают указатель данных звука до 32 бит:

```c
g_GraphicsBuffers[v6] = (int)(INT_PTR)(a4 + 1);
dword_411DB4[v6]      = (int)(INT_PTR)(a4 + 1);
```

а `MixAudioBuffers` восстанавливает его через **знаковое расширение**:

```c
v6 = (int *)(INT_PTR)v3[1];          /* audio.c:806 */
```

На x86 это no-op. На x64 ломается, если данные звука лежат в 2–4 ГБ
(бит 31 установлен → адрес становится `0xFFFFFFFF…`). Починить «в лоб»
**нельзя**: поле объявлено как `int[]` в авто-генерируемом
`game_globals_struct.h`, который обязан совпадать с оригинальным EXE
байт-в-байт, и свободного места под 64-битный указатель в слоте из 4 int
нет. Требует отдельного решения (боковая таблица указателей вне структуры).

По той же причине `audio.c:676` (`g_hMainWindow[0] = (DWORD_PTR)g_MainWindow`)
усекает HWND до 32 бит.

## Маскирование отказа открытия устройства

Если `SdlWave_Open` не откроется, это не видно никому:

```c
audioInitResult = InitWaveOut(pHwnd);          /* audio.c:541 */
if ( InitMidiOut() | audioInitResult )         /* audio.c:542 — хватает успеха ТОЛЬКО MIDI */
{ ...переподключает g_pfn*... return 1; }      /* wave-указатели живы, а s_WaveDev == 0 */
...
return 1;                                      /* audio.c:696 — InitGraphics врёт всегда */
```

Дальше `SdlWave_Queue` возвращает 0 сразу (`sdl_backend.c:1511`), а
`SdlWavePump` выходит на `!SdlWave_IsOpen()` — эффекты мертвы, музыка играет,
`InitGraphics` вернул успех. Единственный след — `SdlWave_Open:
SDL_OpenAudioDevice failed: …` (нужна отладочная сборка).

## Чек-лист, когда появится свежий лог падения

1. Найти `auxMainLoop: startResourceId=` — по ним понять, где именно упало.
2. `Select-String 'TriggerSoundSlot'` — есть ли `muted`? Если да →
   `g_RenderingInProgress`/`g_SoundEnabledFlag`, механика из таблицы отброшена
   заново открыта.
3. `Select-String 'SdlWave_Pause'` — `: 1` без `: 0`?
4. `Select-String 'SetWaveVolume: 0'`.
5. `Select-String 'SdlWave_Open|SdlWave_Clear|SdlWave_Queue'` — посмотреть,
   застывает ли `stillQueued`.
6. Сверить последний `TriggerSoundSlot` с ближайшим `SdlWave_Queue`: если
   номер звонка < 8, это достоверно; если ≥ 8 — **нужен снятый троттлинг**.

Снятый троттлинг (`sdl_backend.c`, условие в `SdlWave_Queue`) — первое, что
стоит сделать перед повторным репро: одна строка в порт-файле, где уже живут
эти диагностики, и лог назовёт первое же слабое звено. Сделать по возврате к
задаче.
