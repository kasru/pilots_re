# Пропадают звуковые эффекты (музыка играет) — расследование от 13.10.2026

Статус: **причина названа и закрыта инвариантом (16.10.2026)** — см. раздел
«Корневая причина и исправление». Симптом воспроизвёлся на Nintendo Switch,
корень — `g_GraphicsState1 > 0` при полностью дренированной очереди
(deferred deadlock), после чего `PlaySoundEffect` выходит до микширования, и
все новые эффекты мертвы до рестарта. Исправление покрывает все пути этой
смерти, включая переход сцены 3→1, где пересброса `state1` нет вообще.
Свежий пользовательский лог с консоли (16.10.2026) разобран ниже — это первая
сессия, где волна умерла на глазах у полных инструментов. Не перепроверяйте
отброшенное заново — идите по чек-листу в конце; все пункты, кроме последнего
(новый лог), для консоли уже выполнены.

### Почему `ProcessVideoCommands` недостижим

- `dword_416338` (таблица смещений внутриигровых роликов, `+0x62C4`)
  **нигде не записывается как указатель**: инициализируется нулём
  (`game_globals_init.h:775`), и далее только *через* него пишется
  (`gameloop.c:528`) и читается (`video.c:403`). Вызов `ExecuteVideoPlayback`
  читал бы `*(DWORD*)0`.
- Запасной вход `CheckGameState()` (`saveload.c:376`) требует
  `g_DisplayMode[1] == 1`, а `g_DisplayMode[1]` = `HIBYTE(pConfigEx->field_24)`,
  и в логе видно `HIBYTE(field_24)=2`.

Соответственно `SdlWave_Pause` / `SdlWave_Pause: 0` в логах отсутствуют не
потому, что катсцен не было, а потому что этот код не исполняется.

## Оставшаяся механика (не подтверждена)

Единственное объяснение, подходящее под все четыре признака симптома
(эффекты мертвы / музыка живёт / рестарт лечит / плавающая):

`PlaySoundEffect` (`audio.c:730-748`) при `a1 >= 0` и `g_GraphicsState1 != 0`
**выходит, не вызывая `MixAudioBuffers`**:

```c
if ( g_GraphicsState1 ) v7 = 0; else v7 = 2;
if ( v7 == 2 )      MixAudioBuffers();
else if ( v7 != 1 ) return 1;      /* v7==0 → выход без микширования */
```

При этом:

- `g_GraphicsState1` присваивается **только** внутри микшера
  (`audio.c:822: g_GraphicsState1 = v0`) и обнуляет его **только**
  `InitGraphics` (`audio.c:686`), то есть старт/рестарт;
- слот освобождается (`*v3 = 0`, `audio.c:814`) тоже только в микшере;
- `MixAudioBuffers` извне зовётся лишь из `SdlWavePump`
  (`sdl_backend.c:1345`, `:1406` — на каждом `SdlBackendPumpEvents`);
- `SdlWavePump` вызывает микшер **только внутри цикла отчёта о завершении
  буферов**, а тот крутится лишь пока растёт `limit = consumed / 2048`,
  то есть пока `SDL_GetQueuedAudioSize` уменьшается.

⇒ Если открытое непаузированное устройство перестаёт дренировать очередь
(`avail == total` → `consumed = 0` → `limit = 0` → цикл не выполняется ни
разу), то `s_WaveIfCount` застревает, слот не освобождается,
`g_GraphicsState1` остаётся > 0 навсегда, и **все дальнейшие эффекты молчат**
до `InitGraphics`, то есть до перезапуска. На Windows MIDI живёт — это там
другое устройство; **на Switch это тот же колбэк** (см. свежий лог ниже).

Что осталось невыясненным: почему открытое непаузированное устройство могло
перестать дренировать. Пауза (`SdlWave_Pause`, `sdl_backend.c:1574`) и закрытие
(`SdlWave_Close`, `sdl_backend.c:1491`) в логе отсутствуют.

## Корневая причина и исправление (16.10.2026)

Названа по логу сессии, где волна умерла на переходе сцены 3→1 при внешне
живой цепочке:

- карта сессии: `startResourceId` 1 → 2 → 1 → 3 → 1;
- очереди wave: сцена 1 — 0, сцена 2 — 35 (с длинной паузой 30390→56128),
  сцена 3 — 277, после возврата 3→1 (80872+) — **0**;
- смерть ≈80240, при этом вотчдог показывает работающую цепочку
  (`state 25: in flight 2/8`), `TriggerSoundSlot` после 80147 не было,
  `no header is free` и `shared ring full` — ни разу, `shared=1`.

То есть в момент смерти: **очередь полностью пуста, in-flight нулевой, а
`g_GraphicsState1 > 0`.** Это deferred deadlock по построению: бит state1
выставляет только микшер (`audio.c:822`) и всегда на микше, который кладёт
байты в очередь; пустая очередь при нулевом in-flight означает, что играть
больше нечем — и снять бит уже никто не может (его гасят только
`CleanupWaveOut`/`InitWaveOut`/`ResetWave`, а переход 3→1 их не проходит, и
`PlaySoundEffect` при `state1 != 0` выходит до `MixAudioBuffers` — раздел
«Оставшаяся механика» выше, теперь подтверждён). Раньше лог переходов state1
в `MixAudioBuffers` был закапан 40 строками — в длинной сессии они уходили в
первые секунды, и защёлкивание было невидимо.

Исправление — **инвариант в `SdlWavePump`** (`audio.c`), а не точечный
пересброс в каком-то одном переходе:

```c
if ( !avail && !s_WaveIfCount && g_GraphicsState1 ) {   /* очередь пуста, играть нечем */
    g_GraphicsState1 = 0;
    DBG_LOG("SdlWavePump: queue idle with state1=%d - cleared", g_GraphicsState1); /* кап */
}
```

- строка `queue idle with state1=N - cleared` печатается ровно там, где
  защёлкивалась смерть — искать её первой;
- строка вотчдога теперь несёт поле `state1 %d` — решающий маркер смерти,
  кап на переходы state1 его не касается;
- ложное срабатывание исключено по построению: выставленный бит всегда
  означает «микшер что-то положил», а пустая очередь с нулевым in-flight —
  что играть нечем.

Проверено на пользовательской сессии после исправления (16.10.2026, 75267
строк): симптом не вернулся — звук во всех сценах подтверждён, инвариант не
срабатывал (0 строк `queue idle` — смерть просто не наступала).

## Диагностическая дыра — какие закрыты (16.10.2026)

Дыра была в том, что диагностики не могли ни подтвердить, ни опровергнуть
механику выше. Закрыто 16.10.2026, всё — после разбора консольного лога:

1. **Троттлинг в `SdlWave_Queue` снят** — логируется каждый буфер (`#N`,
   nonzero, stillQueued, vol). Скорость — один звонок на 2048 сыгранных байт
   (5,4/с во время звука, ноль в тишине), так что «каждый» ничего не стоит,
   а именно вызовы `#8`/`#9` были невидимы в прошлой сессии.
2. **`SdlWave_Close` теперь логирует** реальное закрытие (был самым тихим
   местом всего wave-пути); drop в общем кольце (`SdlWave_Queue: shared ring
   full …`) тоже печатается каждый раз, до 40 строк.
3. **`GetNextWaveBuffer` логирует свой waveOutReset-фолбэк** («no header is
   free», до 40 строк) — самый тихий и самый важный момент: все заголовки
   INQUEUE = отчёты о завершении умерли, и движок сбрасывает очередь.
4. **В `SdlWavePump` добавлен вотчдог**: раз в 2 с, пока есть pending или
   in-flight, печатается строка
   `SdlWavePump: state N/120 - pending … game bytes, ring … frames, in flight …/8, queued total …, limit … reported …`,
   где `ring` — реальная глубина кольца (`SdlWave_RingDepth`), против учёта
   `SdlWave_Queued`. `pending > 0 при ring = 0` печатается с меткой
   `DESYNC` — это первая из двух оставшихся механик; полное кольцо — вторая.
   Тишина (ничего не ждёт) не печатает ничего, кап 120 строк = 4 минуты
   перед смертью, которых хватает, потому что смерть приходит в первые
   минуты после последнего звука.

Как читать лог, если он появится:

- `TriggerSoundSlot: slot=N` **без** `muted` + **отсутствие** `SdlWave_Queue`
  рядом → кандидат на механику выше, но **нельзя** доверять при
  `s_WaveQueueCalls >= 8` — троттлинг;
- `SdlWave_Queue: … stillQueued=…` с застывшим значением при растущем числе
  звонков → устройство не дренирует, это и есть предпосылка;
- `SdlWave_Pause: 1` без парного `: 0` → другая, уже отброшенная механика;
- `SdlWave_Open: SDL_OpenAudioDevice failed` / `device gave … refusing` →
  устройство не открылось, `InitDirectDraw_Win95` это маскирует (см. ниже).

## Отдельно: латентный x64-баг указателя (не эта проблема, но найден)

`audio.c:725-726` усекают указатель данных звука до 32 бит:

```c
g_GraphicsBuffers[v6] = (int)(INT_PTR)(a4 + 1);
dword_411DB4[v6]      = (int)(INT_PTR)(a4 + 1);
```

а `MixAudioBuffers` восстанавливает его через **знаковое расширение**:

```c
v6 = (int *)(INT_PTR)v3[1];          /* audio.c:806 */
```

На x86 это no-op. На x64 ломается, если данные звука лежат в 2–4 ГБ
(бит 31 установлен → адрес становится `0xFFFFFFFF…`). Починить «в лоб»
**нельзя**: поле объявлено как `int[]` в авто-генерируемом
`game_globals_struct.h`, который обязан совпадать с оригинальным EXE
байт-в-байт, и свободного места под 64-битный указатель в слоте из 4 int
нет. Требует отдельного решения (боковая таблица указателей вне структуры).

По той же причине `audio.c:676` (`g_hMainWindow[0] = (DWORD_PTR)g_MainWindow`)
усекает HWND до 32 бит.

На Switch (aarch64) этот баг безвреден: пул низкой памяти (`Shim_AllocLow`)
отдаёт адреса вида `0x20xxxxxx`, бит 31 там не установлен, так что усечение
до 32 бит и обратное знаковое расширение сохраняют адрес — измерено на той же
консольной сессии, где эффекты молчали: `PlaySoundEffect` работал, слоты
регистрировались, усечение ни при чём.

## Чек-лист, когда появится свежий лог

0. **`SdlWavePump: queue idle with state1=N - cleared`** — главный маркер
   этой смерти: инвариант сработал там, где очередь опустела при живом бите.
   И `state1 %d` в строках вотчдога — смотреть в момент смерти (капа у него
   нет).
1. Найти `auxMainLoop: startResourceId=` — по ним понять, где именно были
   эффекты.
2. `TriggerSoundSlot` — есть ли `muted`? Если да →
   `g_RenderingInProgress`/`g_SoundEnabledFlag`, механика из таблицы отброшена
   заново открыта.
3. `SdlWave_Pause` — `: 1` без парного `: 0`? `SetWaveVolume: 0`?
4. **`SdlWavePump: state` — главный инструмент.** Пока цепочка живёт, pending
   убывает и ring держит обещанные байты. В момент смерти: `DESYNC` в строке
   (pending > 0 при пустом кольце — десинхрон счётчиков, первая из двух
   оставшихся механик) либо ring у предела 32768 (потребитель съедает
   медленнее, вторая). Строка печатается каждые 2 с только пока что-то
   ждёт, так что первая застывшая строка и есть момент смерти.
5. `GetNextWaveBuffer: no header is free` — срабатывал ли фолбэк
   waveOutReset: если да, отчёты о завершении умерли ещё до него.
6. `SdlWave_Close:` — не закрылось ли устройство посреди сессии.
7. `SdlWave_Queue: #N … stillQueued=…` — троттлинга больше нет, каждый
   звонок на виду: сверить номер последнего звонка с последним
   `TriggerSoundSlot` (цепочка «триггер есть, звонков нет» = умерла
   доставка, «звонки есть, stillQueued застыл» = умер потребитель).
