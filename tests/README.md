# tests

Скрипты проверки. Проект не имеет тестов, линтера и CI — **единственная верификация это сборка
и запуск игры с чтением debug-лога** (`AGENTS.md`). Эти скрипты автоматизируют именно это.

## windows/

Запуск через PowerShell 7 (в `PATH` его нет, `pwsh` на машине — это PS 5.1, без тернарного
оператора и с BOM при `Set-Content -Encoding utf8`):

```
& "$env:ProgramFiles\PowerShell\7\pwsh.exe" -NoProfile -File tests\windows\pfuzz.ps1
```

| Скрипт | Что делает |
|---|---|
| `buildall.ps1` | Собирает все 4 конфигурации подряд, печатает только SUCCESS/FAILED |
| `x86check.ps1` | Собирает x86 debug **последним** (чтобы `SDL2.dll` была x86), гоняет 12 с из чернового каталога без роликов, сверяет маркеры `auxMainLoop=1` / `GameMainLoop=2` и отсутствие исключений |
| `pfuzz.ps1` | Основной харнесс: стартует x64 debug, входит в сцену 1, сыплет кликами `PostMessage` по сетке + клавиатура, скриншоты, поиск `EXCEPTION: 0xC000` |
| `audio.ps1` | Тест кнопок звука и музыки на нижней панели (см. ниже). Печатает PASS/FAIL по каждой проверке, код выхода 0 = всё сошлось. Параметр `-Arch x86|x64` гоняет **один и тот же** сценарий на выбранной архитектуре — он для сравнения двух сборок, см. «MIDI-значения x86 против x64» |
| `rundir.ps1` | Не скрипт запуска, а библиотека: `New-GameRunDir` собирает черновой каталог `%TEMP%\pilots_rundir` с жёсткими ссылками на exe, `SDL2.dll` и данные `PILOTS.EXE` — **без** `MOVIES`. См. ниже, почему ролики держат вне каталога запуска. Плюс детектор стартового диалога (`Get-StartupDialog` / `Report-StartupFailure` / `Clear-StartupDialogs`), см. ниже |
| `fuzz.ps1`, `nav.ps1` | Более ранние версии того же навигационного прогона (оставлены как референс) |
| `play.ps1` | «Человеческий» прогон: клик → выдержка 4 с, чтобы анимации и диалоги успевали отыграться |
| `realfuzz.ps1` | То же, но реальным вводом мыши (`SetCursorPos`+`mouse_event`) |
| `relfuzz.ps1` | Прогон release-сборки (без `DBG_LOG`) — конфигурация, в которой пало у пользователя |
| `probe.ps1` | Сборка x64 debug + `pfuzz` одной командой |
| `check_x64_file.bat` | Пофайловая компиляция MSVC x64: показывает предупреждения о несовпадении указателей (это и есть сигнал миграции LP64) |
| `analyze_probe*.ps1` | Разбор логов компиляции: гистограмма `C4xxx`, фильтр «указательного» класса предупреждений |

### Как кликать в игру

Координаты — **логические** (клиент 640×480). Рабочий приём: `PostMessage(hwnd, 0x0200, 0, LP)`
→ `0x0201` с `wParam=1` → `0x0202` с `wParam=0`, где `LP(x,y) = ((uint)y<<16)|((uint)x&0xFFFF)`.

`PostMessage` предпочтительнее реального ввода: он адресует сообщение прямо в окно игры, не требует
фокуса и не двигает курсор. Реальный ввод (`mouse_event`) уходит в то окно, что под курсором, а
Windows не даёт фоновому процессу увести фокус — отсюда «клики мимо».

Проверять доставку надо по самой игре: `SdlGameWndProc: msg=0x201 wp=0x1 lp=0x1C0002A` — это
ровно `(42,448)`.

`SetCursorPos` требует **физических** координат = логические × 1.25 (процесс DPI-aware, игра — нет).

### Тест кнопок звука и музыки (`audio.ps1`)

На экране выбора уровня (это и есть стартовый экран) нижняя панель несёт пять кнопок — картинка плюс
вертикальная подпись справа, логическое `y=448`:

| № | Подпись | x | Что делает |
|---|---|---|---|
| 1 | ИГРА | ~66 | запускает сцену, панель меняется на инвентарную |
| 2 | **МУЗЫКА** | ~196 | MIDI-музыка вкл/выкл (саксофонист меняет позу) |
| 3 | **ЗВУК** | ~324 | звуковые эффекты вкл/выкл (кот с микрофоном ложится) |
| 4 | ПОИСК | ~452 | |
| 5 | ПОХОД | ~582 | |

Попадает только в **центр** кнопки — клик по подписи или по краю ничего не делает.

Скрипт проверяет три обещания панели, выводя объективные, а не «на глаз» признаки:

1. картинка на кнопке перерисовывается на каждый клик (пиксельное сравнение зоны 90×42 двух скриншотов);
2. тумблеры **чередуются** — выкл, вкл, выкл, вкл. Раньше они умели только выключать: натив
   `Native_GetSystemFlag` — единственный `__fastcall` в таблице, и на x64 аргумент-селектор приходил
   не с того слота стека, поэтому скрипт всегда уходил в «выключено» и картинка не менялась;
3. MIDI и эффекты действительно подчиняются флагу — по логу проверяется, что громкость доезжает до
   0 и обратно до 255 (затухание идёт по шагу за кадр, поэтому скрипт ждёт конца ramps), трек
   `SwitchMusicTrack` запускается, а `TriggerSoundSlot` в сцене срабатывает и **не** пишет `muted`.

Переключатель задаётся одним аргументом натива `Native_SetSystemFlag`: `2/3` — звук выкл/вкл,
`4/5` — музыка выкл/вкл. По нему же считывается состояние.

**Игра запускается не из `SRC\`, а из чернового каталога** — см. следующий раздел.

### Каталог запуска (`rundir.ps1`)

`main.c` разыскивает `.\PILOTS.EXE` (собственные данные игры) и ролики `.\movies\...` относительно
**текущего каталога процесса**, поэтому exe надо запускать оттуда, где лежат данные. Но в этот
каталог **не кладут `MOVIES\`** — чтобы интро пропускалось и прогон был детерминированным:

- **64-бит.** Путь AVI через MCI на этом Windows сломан: `mciSendCommandA(MCI_OPEN)` не возвращает
  ошибку, а **падает внутри `winmm.dll`** (Windows Error Reporting называет модуль-виновник
  `WINMM.dll`, смещение `0x176fa`). Сам драйвер `mciavi32.dll` на месте, кодек `msrle32.dll` тоже —
  ломается именно 64-битный MCI-диспетчер. Теперь это ловится в `video.c` (`MciSendCommandGuarded`)
  и видео просто пропускается, но тестам детерминизм нужен в любом случае.
- **32-бит.** WoW64 находит рабочий драйвер, ролик проигрывается — и 12-секундное окно
  `x86check.ps1` уходит на него целиком, из-за чего маркеры `auxMainLoop`/`GameMainLoop` съезжают
  просто потому, что ролики установлены.

`New-GameRunDir` собирает `%TEMP%\pilots_rundir` с жёсткими ссылками на exe, `SDL2.dll` и данные
`PILOTS.EXE` (без копирования ~15 МБ; `mklink /H` прав не требует — в отличие от симлинков).
Сборку надо выполнять **до** вызова функции, иначе ссылка укажет на предыдущий exe.

### Стартовый диалог 0xC000007B — это не «падение»

Обе архитектуры импортируют **одинаково названный** `SDL2.dll`, так что запускается только та
сборка, которую собирали последней. Если запустить x64-exe с 32-битной `SDL2.dll` (или наоборот),
LoadLibrary отваливается ещё до `main()`: ни окна, ни лога, а Windows показывает модальное
«Ошибка при запуске приложения (0xc000007b)». Такое легко принять за регрессию в коде игры.

Два подводных камня, из-за которых автоматическое распознавание не тривиально:

- Диалог **не принадлежит игровому процессу** — он живёт в чужом pid (загрузчик поднимает его
  сам). Фильтр окон по `$p.Id` его просто не находит, `MainWindowHandle` остаётся 0.
- `MainWindowHandle` при отсутствии игрового окна может вернуть **сам диалог** — тогда харнесс
  начинает «кликать» по нему мышью, получает 0 подтверждений и печатает загадочное
  `CRASHED`. Поэтому окно дополнительно проверяется по классу (`#32770` ≠ игровой `SDL_app`).

`rundir.ps1` поэтому ищет `#32770` по всем окнам, сопоставляя заголовок с именем **exe** (`<имя>.EXE`,
а не просто именем процесса: `PILOT_RV` — подстрока `PILOT_RV_x64`, иначе харнесс x86 подхватит
чужой, оставшийся от прошлого прогона, диалог), собирает текст статических контролов (именно там
лежит код ошибки, в заголовке его нет) и жмёт кнопку, чтобы ничего не зависло. `New-GameRunDir`
заодно чистит такие диалоги от прошлых прогонов.

Вызывается из `pfuzz.ps1`, `audio.ps1` и `x86check.ps1` в момент «окно так и не появилось» —
вместо безликого `no window` харнесс печатает текст диалога, расшифровку кода и выходит с кодом 1.

## MIDI-значения x86 против x64

На логах видно два числа, которые между архами расходятся. Оба — **тайминг, а не разница
архитектур**; ведущего значения нет ни у одного.

| Строка лога | Значение | Статус |
|---|---|---|
| `SdlMidi_Open: libADLMIDI ready: emu=… bank=… rate=…` | `emu=Nuked OPL3 (v 1.8) bank=68 rate=44100` | **Инвариант**, совпадает всегда |
| `SdlMidi_ShortMsg: first message` | `0xB9` | **Инвариант** |
| `SetMidiVolume` (лесенка при переключении кнопки) | `0,17,34,…,238,255` в обе стороны | **Инвариант**, последовательность байт-в-байт одинакова |
| `SwitchMusicTrack` | `track=1,track=1` | **Инвариант** |
| `SdlMidi_Pump: first audible PCM (X of 1024 samples nonzero)` | 937 или 941 | Тайминг |
| `SdlMidi_Reset: N messages processed` | 1 строка на x86, 2 на x64 | Тайминг |

Почему так.

**`first audible PCM`.** Число ненулевых сэмплов в *первом* отрендеренном куске зависит от того,
сколько MIDI-событий успело дойти до синтезатора к этому моменту, а это зависит от того, когда
10-мс таймер `timeSetEvent` успел сработать впервые. Проверка: в простое 10 с обе архитектуры
дают ровно 937, а в интерактивном сценарии одна и та же x86-сборка по разным прогонам даёт то
937, то 941 — то есть число не привязано к архитектуре вообще.

**`SdlMidi_Reset`.** `ResetMidi()` вызывается и на старте трека (`StartMidiPlayback`), и на
останове (`StopMidiPlayback`), и при доигрывании песни; строка печатается только если с прошлого
сброса накопились события (`s_MidiMsgCount > 0`). Между парой Stop/Start, идущих почти вплотную,
10-мс таймер успевает дать ровно один тик либо не успевает вовсе — и тогда одни и те же 4 вызова
дают на x86 одну строку (второй вызов печатает 0 и молчит), а на x64 две. Доказательство —
временная инструментация `SdlMidi_Reset` (счётчик вызовов + повторное логирование «первого
сообщения» после каждого сброса): последовательность вызовов **#1…#4 одинакова на обеих
архитектурах**, расходится только число сообщений, уложившееся в один тик, — 0 против 56.

Итог: исправлять в движке нечего — поведение идентично. Обе диагностические строки помечены
комментарием в `sdl_backend.c`, чтобы их снова не приняли за контрольные значения; опираться
на них как на регрессию нельзя. Чтобы сравнить архитектуры честно, гоняют один и тот же сценарий:
`audio.ps1 -Arch x86` и `audio.ps1 -Arch x64` (скрипт сам пересобирает нужный exe, чтобы в `SRC`
оказалась подходящая по разрядности `SDL2.dll`).

## linux/

Запуск обычным `sh`. Скрипты больше не привязаны к `/home/ntadmin/...` — переходят в корень
репозитория через `cd "$(dirname "$0")/../.."`.

| Скрипт | Что делает |
|---|---|
| `test_wm_freeze.sh` | Регрессия_WM: клиент обязан оставаться 640×480 через любой цикл maximize/restore/fullscreen/iconify; залипание 0×0 после restore замораживает рендер |
| `diag_hang.sh` | Тест завершения: SIGUSR1 → штатный выход; если через 10 с жив, ловим SIGSEGV, чтобы обработчик игры напечатал бэктрейс залипшей точки |
| `diag_video.sh` | Смоук-тест видео: интро+старт через ffmpeg-MCI, потом чистый выход |
| `x11ctl.py` | X11/EWMH-драйвер через ctypes+libX11 — заменяет xdotool/wmctrl; нужен первым двум скриптам |

## Рабочий процесс

1. `buildall.ps1` — все 4 конфигурации собираются.
2. `x86check.ps1` — 32-бит не изменился (байт-в-байт тот же код).
3. `pfuzz.ps1` — 64-бит живой, 0 исключений.
4. `audio.ps1` — кнопки звука и музыки на панели переключаются в обе стороны.
5. Пересобрать x64 последним, иначе `SDL2.dll` останется x86 и `PILOT_RV_x64.EXE` не стартует
   (в этом случае харнесс теперь сам напечатает текст стартового диалога и расшифровку 0xC000007B).

Надо помнить: **release-сборки пишут `DBG_LOG` в пустоту.** Падение воспроизводить только на
debug-сборке — иначе в логе не окажется ни исключения, ни дампа регистров.
