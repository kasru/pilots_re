# AGENTS.md

## What this repo is

Byte-faithful C reconstruction of the engine from the 1996 game «Братья Пилоты», decompiled from the original `PILOTS.EXE` (IDA Hex-Rays). All game logic lives in bytecode scripts inside the original game's data file — the C code is just the interpreter/player.

- All sources are flat in `SRC/` (no subdirs, no packages).
- Docs are in Russian: `SRC/docs/README.md` → per-subsystem pages (`architecture.md`, `scripting.md`, …). Trust code over docs when they disagree. They predate the SDL2 port — window/present/audio specifics live in `SRC/sdl_backend.c`.
- SDL2 port: window, input, present and PCM sound effects go through SDL2 (`SRC/sdl_backend.c` subclasses SDL's wndproc so the game's `Host_MainWndProc`/`Host_AviWndProc` still see raw Win32 messages). MIDI music renders through **libADLMIDI** (OPL3 emulation, submodule `third_party/libADLMIDI`) into its own SDL queue-audio device (`SdlMidi_*` in `sdl_backend.c`) — only the winmm 10 ms event timer (`timeSetEvent`) survives from the old midiOut path. AVI video stays on MCI.

## Build (the only automated verification — there are no unit tests, linter, or CI)

- One bat, `SRC\build-vs2022.bat [debug|release] [x86|x64]` (defaults: release x86), `pushd`ing to SRC so it works from any CWD. `SRC\build.bat` is the older x86-only cut for a VS18 (14.50) machine and is kept as-is; `build-vs2022.bat` is the one this machine can run (VS2022 Community 14.44). One place holds the whole recipe, and there is no libADLMIDI block in either bat — Windows music is real winmm midiOut, so the OPL3 synth is a Linux/Switch-only library (see `CMakeLists.txt`):
  - x86 (the proven baseline) → `SRC\out\x86\PILOT_RE.EXE` (+ `.pdb` in debug, which is the only flavour that passes `/Zi`).
  - x64 → `SRC\out\x64\PILOT_RE_x64.EXE`. Separate name so it can sit next to the x86 build; the 64-bit image is pinned below 2 GB with `/BASE:0x10000000 /DYNAMICBASE:NO`, because the game stores addresses in 32-bit `int` and its static buffers must fit a signed int32. x86 gets neither flag — the loader already puts it there.
  - **One output dir per arch** (`out\x86`, `out\x64`), each with its own `SDL2.dll`. This is what makes both arches runnable at once: they import the same `SDL2.dll` name, so before the split only the last-built arch could actually run, and the harnesses had to rebuild their arch first. Now they do not.
  - The exe must never be named `PILOTS.EXE`: the engine opens its data file as `.\PILOTS.EXE` (CWD-relative), so a rebuilt exe named `PILOTS.EXE` would read *itself* as game data — and it must never be copied over the original game's `PILOTS.EXE` (that file holds the resources). Run the exe from a directory containing the original game data.
  - Flags per flavour: debug is `/Od /Zi /MTd /D_DEBUG`, release is `/O2 /MT /DNDEBUG` — static CRT, so the exe carries no vcruntime/msvcp dependency. Both pass `/std:c17 /W4 /WX /utf-8 /D_CRT_SECURE_NO_WARNINGS`, and SDL2's headers are marked external (`/external:W0 /external:I`) so that `/WX` cannot be tripped by them. `/utf-8` is not cosmetic: the sources are UTF-8 and the machine code page is not, and every Cyrillic byte lives in a comment or a string.
  - `SRC\pilots.rc` is only one `100 ICON "pilots.ico"` statement, and `SRC\pilots.ico` is deliberately **not** in the repo — it is carved out of the original `PILOTS.EXE`, so it is game data like everything else in that file. Without the icon the build still succeeds (the exe just has no icon of its own); nothing in the engine loads it — `host.c` defines `HOST_ICON_RESOURCE = 100` and never calls `LoadIcon`, SDL never calls `SDL_SetWindowIcon` — so it is Explorer/Alt-Tab that notice its absence, not the game. There is no `VERSIONINFO` and no version to bump here, unlike the sdl2 branch's `.rc`.
- Intermediate `.obj` files go to `SRC\out\<arch>` — one dir per arch, so the builds coexist and never stomp each other: `out\x86`, `out\x64`. A debug build also drops its `/Fd` compiler PDB there; release passes no `/Zi`, so it has none. The exe, `SDL2.dll` and the linker `.pdb`/`.ilk` land in the same dir (the game data stays in `SRC\` itself), which is what makes both arches runnable at once — `rundir.ps1` `Get-OutDirForExe` reads that layout back. There is no `.map`: the bat passes no `/MAP`.
- Toolchain paths are hardcoded at the top of the bat: VS 2022 Community MSVC `14.44.35207`, Windows SDK `10.0.26100.0` (x86 uses `Hostx86\x86`, x64 `Hostx64\x64`). Edit `VCTOOLS` / `WINSDK` / `SDKVER` there if your install differs. SDL2 headers/libs come from `third_party\SDL2` (include/, plus lib/x86/ or lib/x64/) — edit `set SDL2=` if it moves.
- **Windows also builds through `CMakeLists.txt`** — the arch comes from the generator, not from a switch in the file: `cmake -S . -B build-win64 -A x64` → `build-win64\Release\PILOT_RE_x64.EXE`, `cmake -S . -B build-win32 -A Win32` → `build-win32\Release\PILOT_RE.EXE`, then `cmake --build <dir> --config Release`. Or Ninja under a `vcvars` prompt (`cmake` is **not** on this machine's `PATH`; what is installed is the copy bundled with VS — `tests\windows\rundir.ps1` `Find-CMake` looks for exactly that, and `Build-GameExe` in the same file is what every Windows harness builds through, so `-Build cmake` reaches the CMake path from any of them). `CMAKE_SIZEOF_VOID_P` is what picks `lib\x64` vs `lib\x86` and the exe name, so both generators share one code path. The bat stays the proven baseline and the CMake branch deliberately mirrors its flags (`/W4 /WX /utf-8`, static CRT, `/BASE:0x10000000 /DYNAMICBASE:NO` on x64) rather than inventing new ones; two traps the branch had to handle are recorded in `CMakeLists.txt` itself — `SRC\winshim` must not be on the include path on Windows (it holds the fake `<windows.h>`, which has no `HMIDIOUT` and breaks `gm.h`), and `_DEBUG` on MSVC must follow the config's CRT, because `debug_log.h` calls `_CrtSetReportMode`, which exists in the debug CRT only.
- Linux uses CMake, not the bats, and keeps **one build dir per architecture** (SDL2/libavcodec are arch-specific, so objects can never be shared):
  `cmake -S . -B build32 -DPILOTS_M32=ON` — 32-bit, the byte-comparable baseline; build it *inside* the `pilots-build` image from `Containerfile`, the host carries no i386 toolchain. `cmake -S . -B build64` — native x86_64; the LP64 `INT_PTR` migration is what lets the generated headers lay out correctly here. `scripts/run_podman.sh` launches the 32-bit build in the container and picks the dir with `PILOTS_BUILDDIR` (default `build32`).
- The **Nintendo Switch** build is CMake too, cross-compiled by devkitA64: `sh scripts/build_switch_podman.sh debug` (modes `build` | `debug` | `clean` | `distclean`) runs inside the `devkitpro/devkita64` image and produces `build-switch/PILOT_RE.nro` (`debug` is the only mode with `_DEBUG` and goes to its own dir `build-switch-dbg/PILOT_RE.nro`, which is the one `BUILDDIR=build-switch-dbg sh scripts/deploy_switch.sh` uploads — the debug log and the crash offsets only mean anything against it). It passes `-DPLATFORM_SWITCH=ON -DCMAKE_TOOLCHAIN_FILE=/opt/devkitpro/cmake/Switch.cmake`; `CMakeLists.txt` needs both — the toolchain sets `CMAKE_SYSTEM_NAME=NintendoSwitch`, which is what makes CMake load `Platform/NintendoSwitch.cmake` and brings `nx_generate_nacp`/`nx_create_nro` into scope for the `.nro` step at the bottom. The base image already ships `switch-sdl2`, `switch-ffmpeg` and `switch-tools`, so unlike the wiliwili-style Switch builds **nothing gets downloaded into the repo root** and `dkp-pacman` is never run (a `-Syu` on a fresh container is the usual way to break it). `clean` must go through the script, i.e. inside the container: CMake bakes the mount path `/data` into the generated Makefiles.
- **Where the Switch's SDL2 and ffmpeg come from: the image already has them.** `devkitpro/devkita64` ships the whole Switch SDK, not just a compiler — 77 `switch-*` packages baked in at image build time from the signed `dkp-libs` repo with devkitPro's own keyring (`switch-sdl2 2.28.5-4`, `switch-ffmpeg 7.1-5`, `switch-tools 1.13.1-1` for `elf2nro`/`nacptool`, `libnx 4.12.0-1`, `switch-pkg-config` for the `aarch64-none-elf-pkg-config` that `FindPkgConfig` runs). So **nothing is downloaded into the repo root and `dkp-pacman` is never run** — that is the whole difference from the wiliwili-style Switch builds, which `curl` `.pkg.tar.zst` files (switch-libmpv, switch-libass, hacBrewPack, switch-nspmini, plus their own switch-ffmpeg) and `dkp-pacman -U` them, because libmpv/libass and the NSP forwarder tooling are not part of the SDK and they want a differently configured ffmpeg on top. Two details worth knowing: `sdl2.pc`'s Cflags carry `-D__SWITCH__` (one of the two places that define it, the other being devkitPro's `Platform/NintendoSwitch.cmake`), which is what every `#ifdef __SWITCH__` in the port layer keys off; and `switch-ffmpeg` contains `ff_msrle_decoder`, the MS RLE decoder the game's own AVI files need through `mci_ffmpeg.c`. The weak point is that the image is pinned only as `:latest`, so a differently-stocked image elsewhere would fail obscurely — `build_switch_podman.sh` therefore runs a pkg-config pre-flight inside the container and fails with the package names instead. If it ever fires, the fix is to put the packages **into the image** (a `--rm` container forgets installs, which is why the filmix scripts reinstall theirs every build): `podman run --name dkp-deps IMAGE dkp-pacman -S --noconfirm switch-sdl2 switch-ffmpeg && podman commit dkp-deps IMAGE`, then point `PILOTS_SWITCH_IMAGE` at it.
- The four CMake knobs the C code leans on and that live only in `CMakeLists.txt`: `CMAKE_C_STANDARD 17` with extensions on (GCC 14+ defaults to C23, where `()` in a declaration means `(void)` — and `game_globals_struct.h` declares the engine's callbacks as `int (*g_pGraphicsFunc)();` and calls them with arguments), `-fsigned-char` (see the Switch bullet below — the one knob here that changes generated code, and only on aarch64), `-Wno-error=` for `-Wincompatible-pointer-types`/`-Wint-conversion` (GCC 14 promoted both from warning to error-by-default, and the decompiled code is full of deliberate IDA-typedef puns that must not be "fixed"), and no `-rdynamic` on the Switch (a static PIE link). All four are no-ops on the older toolchains, so build32/build64 behaviour is unchanged — verified: `x86check.ps1` PASS and `tests/linux/datapath.sh` 15/15.
- **Adding a `.c` file means editing `CMakeLists.txt` (`GAME_SOURCES`) — and nothing else on Windows.** The bat does not keep a list at all: it runs `cl … /c *.c` and links `"%OUTDIR%\*.obj"`, so it picks up whatever sits in `SRC\`. That asymmetry is worth knowing in both directions: a file `GAME_SOURCES` lacks builds fine on Windows and silently vanishes on Linux/Switch, and a file that must *not* build on Windows cannot be left out of the bat — it has to switch itself off, which is exactly what `win32_shim.c` and `mci_ffmpeg.c` do (`#ifndef _WIN32` down to the last line, so the bat compiles them into empty TUs and never notices). There are no scratch files in `SRC\` any more — `test_cast.c`/`test_wave.c` from the sdl2 branch are gone — so today every `.c` in `SRC\` is meant to build everywhere by one of those two mechanisms. libADLMIDI's compile blocks live only in `CMakeLists.txt` and only under the non-Windows branch; if a submodule update changes its source set or options, that is the one place to change.
- Compiles with `/W4` and `/WX` — warnings are errors, which is why SDL2's headers are marked `/external:W0` (a warning from a third-party header must not fail the build). The one concession is `-Wno-error=` for two GCC warnings on the Linux/Switch side (see the CMake-knobs bullet).
- `.gitignore` covers build droppings (`*.obj`, `*.exe`, `*.pdb`, `*.map`, `*.ilk`, `*.dll`, `*.res`, `*_debug.log`), every CMake build dir (`build*/` — `build/`, `build32/`, `build64/`, `build-switch/`), plus `*.SAV` and the icon carved out of the game (`SRC/pilots.ico`) — don't force-add them.

## Tests (manual harnesses, driven by scripts — still no unit tests, linter, or CI)

Everything for verifying a change lives in `tests/`, split by OS; `scripts/` holds the launch/deploy helpers — `run_podman.sh` (Linux), `build_switch_podman.sh` / `deploy_switch.sh` / `run_switch_nxlink.sh` / `decode_switch_crash.sh` (Switch), `make_switch_icon.ps1`. `tests/README.md` has the full per-script table — read it before touching a harness. Highlights:

- **Run them with PowerShell 7, from a file:** `& "$env:ProgramFiles\PowerShell\7\pwsh.exe" -NoProfile -File tests\windows\<name>.ps1`. Never `pwsh -Command`, never the `pwsh` on PATH — that is PS 5.1 (no ternary, no `[UIntPtr]`, mangles embedded quotes, `Set-Content -Encoding utf8` writes a BOM).
- Harnesses resolve `SRC` from their own location (`$PSScriptRoot\..\..`), so any checkout path works.
- `buildall.ps1` — all four combinations (`debug|release` × `x86|x64`) back to back, prints SUCCESS/FAILED only; `-Build bat|cmake` walks the four through either path, and both are green 4/4 before a commit that touches either. `x86check.ps1` — builds x86 debug, plays 12 s from the scratch dir and asserts the baseline markers `ENTER: WinMain`, `First present: 640x480`, `GmGame_Initialize: ok`, `ENTER: GameMainLoop` ≥1, zero `EXCEPTION: 0xC000` — this is how a 64-bit/LP64 change gets proven to leave 32-bit behaviour identical. `-Build bat|cmake` (default `bat`) switches where the exe comes from: the .bat into `SRC\out\x86`, or a CMake build into `build-win32`, which the harness configures itself (`-A Win32`) if nobody did. The measure part is identical either way — the point is that both build paths must produce the *same* markers, so the CMake Windows port is checked against the .bat rather than trusted. Each arch has had its own `SDL2.dll` since `out\x86`/`out\x64`, so "only the last-built arch runs" no longer applies.
- **Every Windows harness builds through one function, and `-Build` means the same thing everywhere** (`Build-GameExe` in `rundir.ps1`): it runs the chosen path and **returns the exe's directory**, so a caller never learns whether it was `out\x64` or `build-win64\Debug`. Harnesses that already built (`x86check`, `clickskip`, `fullscreen`, `moviefs`, `relfuzz`, `probe`, `buildall`) take `-Build bat|cmake` defaulting to `bat`; the ones that never built (`hotspots`, `datapath`, `stretch`, `play`, `fuzz`, `nav`, `realfuzz`) take `-Build none|bat|cmake` defaulting to `none` — i.e. their old behaviour, running whatever sits in `out\<arch>`. `audio.ps1` kept its own older sense (`-Build` = build at all) and got `-BuildVia bat|cmake` for the path; `pfuzz.ps1` got `-FromDir`, which is how `probe.ps1` hands it the dir it just built. Two traps, both already paid for: a function that prints to the *output* stream breaks `$dir = Build-GameExe` (the text gets captured as if it were the path — hence all its status lines go through `Write-Host`), and **the engine takes its data next to the image, not from the CWD** (`WinMain` → `GetModuleFileNameA` → `Host_ResolveGameFilePath` swaps the exe's own name for `PILOTS.EXE` in place), so `Build-GameExe` calls `Stage-GameDataForExe` to hardlink `PILOTS.EXE` into the build dir. Without that a CMake dir has no data at all and the game raises the OS "no resources" box, which no harness dismisses: no window, a 3-line log ending at `SDL video driver`, and the harness reporting a crash for an undismissed dialog (`nav.ps1 -Build cmake` did exactly this until the staging landed; the .bat dir only ever looked healthy because someone had put `PILOTS.EXE` there years ago).
- `audio.ps1` drives the music/sound panel buttons and asserts they alternate; `-Arch x86|x64` runs the *same* click script on either build (default x64), which is the only honest way to compare the two — several MIDI log values look arch-specific but are timing. `rundir.ps1` supplies the scratch run dir and the startup-dialog detector (below).
- **A wrong-arch `SDL2.dll` does not crash, it blocks.** The exe fails to load before `main()`, so there is no window and no log, and Windows shows a modal "Ошибка при запуске приложения (0xc000007b)" — which reads as "приложение падает". Two traps make it hard to automate: the box is owned by a **different** pid (not the game's, so filtering by `$p.Id` misses it and `MainWindowHandle` stays 0), and `MainWindowHandle` can also return the dialog itself, in which case the harness "clicks" it and reports a phantom crash. `rundir.ps1` therefore matches `#32770` windows on `<exe>.EXE` in the *title* (`PILOT_RE` is a substring of `PILOT_RE_x64`, so a bare process-name match grabs the other arch's leftover box), collects the Static children's text (the code is in the body, not the title) and clicks the button; `New-GameRunDir` clears leftovers from earlier runs first.
- `pfuzz.ps1` is the workhorse: starts x64 debug, walks into scene 1, sprays clicks + keystrokes, screenshots, greps the debug log for `EXCEPTION: 0xC000`. `relfuzz.ps1` is the same against release. `play.ps1` dwells 4 s per click so animations/dialogue can settle; `realfuzz.ps1` uses real `SetCursorPos`+`mouse_event` input. `probe.ps1` = rebuild x64 debug + `pfuzz` in one go.
- `clickskip.ps1` is the one deliberate exception to "no real cursor": it puts the cursor on the centre of a **playing** movie, because a click *on* the video is swallowed by mciavi32's `AVIWnd32` child window and never reaches the game window's skip path. `Host_AviWndProc` (host.c) does **not** subclass that child — the child runs clicks through `DefWindowProc`, so `WM_PARENTNOTIFY` arrives at the parent on its own, and that case is the whole skip chain (the code says so in a comment, and the harness is what measured it: a real click on the child stops the movie in seconds against INTRO's ~34 s, with the stop branch logging before `PlayAvi: end`). It copies `SRC\MOVIES` into the shared scratch dir and **removes them in a `finally`** — that dir's contract is "no movies" and loose `.AVI`/`.BMP` files in the CWD are exactly what the engine looks for, so leftovers shift `x86check`'s markers. Asserts `PlayAvi: MCI device` → `PlayAvi: click on the AVI child (WM_PARENTNOTIFY …)` (or `click on the game window`) → `PlayAvi: end playing=`. One latent defect this harness carried: when a foreign window sits under the cursor the script falls back to posting the click at the game window, and that line called `[CS]::PostMessage` which no revision of the class ever declared — the fallback was simply never taken, because `AVIWnd32` always won the cursor. It did take it once (a foreign `MKSEmbedded` window on top), reported `AVIWnd32 is not under the cursor` and then died on the missing P/Invoke; the method is declared now, so the fallback is a real path rather than a comment.
- **Clicking, not driving the real cursor.** Logical 640×480 coords; `PostMessage(hwnd, 0x0200,0,LP)` → `0x0201,wp=1` → `0x0202,wp=0` with `LP(x,y) = ((uint)y<<16)|((uint)x&0xFFFF)`. It needs no focus and moves no cursor, whereas real input goes to whatever window is under the pointer and Windows refuses `SetForegroundWindow` from a background process — hence "clicks land in another window". Confirm delivery by the game's own line `SdlGameWndProc: msg=0x201 wp=0x1 lp=…`. `SetCursorPos` needs **physical** coords = logical × 1.25 (the process is DPI-aware, the game window is not) — or call `SetProcessDPIAware` first and stay in physical throughout, which is what `clickskip.ps1` does.
- `fullscreen.ps1 -Arch x86|x64` covers the borderless-fullscreen port feature (`-fullscreen`, Alt+Enter): window covers the screen, 4:3 picture letterboxed and centred in the 16:9 client, a click in its centre reaches the game with **mapped** coordinates and stops the playing movie, `AVIWnd32` sits at the picture's centre, Alt+Enter toggles both ways. It is the only harness that asserts **pixels**, not log strings — `PrintWindow`+`PW_RENDERFULLCONTENT` (DWM's frame, immune to z-order, which matters because a fullscreen game window is almost always underneath) plus the renderer's viewport equaling its output. The picture itself is asserted **positionally**: the bbox of the non-empty region (a column/row counts as content at ≥25% occupancy, so the tiny bright cursor cannot blow it up) must match the layout rect from the log in *either* logical or physical space (±6 px) **and** keep a 4:3 aspect (±0.02). The old check — the painted fraction *inside* the expected rect — passed a build whose picture was shoved right and cropped by the buffer edge (0.59 either way, while the bbox read 460,0-1532,860 against 192,0-1343,863, aspect 1.246 vs 1.333); the bbox form was proven by that negative test. Log checks alone had passed the broken build too (see the runtime gotcha below).
- `hotspots.ps1 -Arch x86|x64` covers the Ctrl-held interactive-object overlay (same port feature as fullscreen, and it deliberately **works on both arches**): counts the markers in the debug log rather than the pixels, because the scene animates by itself — two resting frames differ by ~34 px while the real markers are ~534. It drives Ctrl with a real `keybd_event`, never `PostMessage`, since the overlay reads the physical key state.
- `datapath.ps1 -Arch x86|x64` covers `-datapath <dir>`: five runs with and without the switch, all reading the **same** debug log (it follows the image, not the CWD) — the switch works, the default is unchanged, a path that cannot be taken degrades instead of dying. The data directory's name carries a space on purpose, which is where a tokenizer that has lost the shell's quoting breaks, and on Linux it is precisely what `main()` in `win32_shim.c` had to be fixed for. `tests/linux/datapath.sh` is the same five runs on Linux.
- **Reproduce crashes on a debug build only** — in release `DBG_*` are no-ops (`debug_log.h`), so a release crash logs neither the exception nor the register dump.
- `check_x64_file.bat` compiles one `.c` at a time under x64 and lets the pointer-mismatch warnings through (they are the signal); `analyze_probe*.ps1` histogram the resulting `C4xxx` logs.
- Linux side: `tests/linux/*.sh` `cd "$(dirname "$0")/../.."` (nothing is hardcoded to `/home/ntadmin/...` any more) and need `x11ctl.py` — an X11/EWMH driver over ctypes+libX11, standing in for xdotool/wmctrl, which the host does not have. Their build dir is `$PILOTS_BUILDDIR` (default `build32`, which only runs inside the `pilots-build` container — the host has no i386 runtime); the native 64-bit build goes to `build64` and is driven by `fullscreen.sh` (it defaults to `BUILDDIR=build64` and fails fast with a message when the exe cannot start). `x11ctl.py` also has `xtest-key <keysym> <down|up>` (libXtst) — Alt+Enter is composed as `Alt_L down` + `Return down/up` + `Alt_L up`, because SDL tracks the modifier state itself.

## Runtime gotchas

- Needs the original game files: `main.c` hardcodes the data path to `.\PILOTS.EXE`, resolved against the **process CWD**. Run `PILOT_RE.EXE` from a directory containing the original `PILOTS.EXE`; video `.avi`/`.bmp` lookup is also relative to that path. `-datapath <dir>` (port feature, parsed in `SdlBackendParseCmdLine`) does a `SetCurrentDirectoryA` **before the game opens anything**, so the data file, `.\movies\...` and the saves all follow it while `main.c` still asks for the literal `.\PILOTS.EXE` — the debug log and the `.hlp` are built from `GetModuleFileNameA` and deliberately stay next to the exe. Verified by `datapath.ps1`/`tests/linux/datapath.sh`; note the Linux `main()` in `win32_shim.c` must put the quotes **back** around argv entries containing spaces, because the shell's quoting that Windows' `lpCmdLine` still carries is gone by the time argv is joined.
- **Nintendo Switch specifics.** The `.nro` is a static aarch64 PIE whose load base the loader picks (`switch.ld` has `__start__ = 0x0`), so the whole image — code, data, `.bss` — spans only ~45 MB from that base. Two things hang off that. (1) **There is no `mmap` on newlib**, so the low-memory pool `GlobalAlloc` hands out (`Shim_AllocLow` in `win32_shim.c`) cannot use the `MAP_32BIT`/hint-a-low-address paths the Linux builds use; on `__SWITCH__` it is a bump allocator over a static array in `.bss`, i.e. at the very bottom of the image, and every hand-out re-checks that the address survives the `int` round trip the decompiled opcodes depend on. `GlobalFree` is correspondingly a no-op there — the only two call sites are the shutdown paths in `audio.c`/`main.c`. (2) **The hbmenu passes no command line**, so `-datapath` is unusable; `SdlBackendParseCmdLine` therefore falls back to `sdmc:/switch/pilots` on `__SWITCH__` *only when* `PILOTS.EXE` is actually in it, otherwise the CWD stays untouched. `sdmc:`-prefixed paths need no special handling: `WinShim_ResolvePath` stats the path as-is first, and libnx's devoptab understands the device prefix, so the case-insensitive walk is never even reached. **The first hardware run confirmed the memory layout**: the log shows `Game_OpenFile: fullPath='sdmc:\switch\pilots\PILOTS.EXE'` and `fd=4`, i.e. the fallback found the data, the low pool handed out addresses that survived the `int` round trip, and the engine read the resource file and reached `GameMainLoop`.
- **On aarch64 plain `char` is UNSIGNED by default, and this code ends loops with it.** `CMakeLists.txt` passes `-fsigned-char` because of it. The symptom was a first-run crash that looked like corrupt data: `Data Abort` inside `LZSSDecompress` writing to a page-aligned address ~26 MB past the buffer, in both Switch configs, on the very first LZSS resource — while the log showed the sizes to be completely sane (`opcode=0x84 sizeFieldBytes=1 n=76 compSize=133`). The copy loop is `char v13 = (BYTE1(v10) & 0xF) + 2; do { ...; --v13; } while ( v13 >= 0 );`, and with unsigned `char` the condition is a tautology: the shipped loop was literally `ldrb / strb [x1], #1 / b` with no counter left in it. After the flag the counter is back as `sub / sxtb / tbz w3, #7`. MSVC and x86 GCC default to signed, which is why x86/x64 never showed it — so this is a **build** property, not a `resource.c` bug to fix locally: the codebase spells signedness out with `(signed char)` in only six places and relies on the x86 default everywhere else. If another arch is ever added, check its `char` default first.
- **How to read a Switch crash.** The log says how far the run got (it is flushed line by line); it cannot say where the CPU stopped, because a CPU exception on newlib is not a POSIX signal — the `SIGSEGV` handler in `debug_log.h` is decoration there, however tidy it looks on Linux. The crash channel is **Atmosphère's own report**: `scripts/deploy_switch.sh --pull-crash` fetches the newest `sdmc:/atmosphere/crash_reports/<tick>_<program-id>.log` over FTP, and `scripts/decode_switch_crash.sh` runs it through `addr2line` in the devkitA64 image. The offsets come out as `PILOT_RE + 0x…` and go **straight** to `addr2line` with no load slide to subtract, because `switch.ld` starts the image at `__start__ = 0x0` — the only lucky thing about debugging on this console. Do not decode `Address:` (that is the abort *target*, data, and the real clue: compare it with the `out=`/`end=` the app logged for the same run) and do not decode `Program ID`.
- **Running a `.nro` from the PC, with the log live: `scripts/run_switch_nxlink.sh`** (devkitPro's `nxlink`, which the image already ships). The one thing that cannot be done remotely is arming hbmenu's netloader: **Y** in hbmenu (B disarms). After that `nxlink -a <ip> file.nro` uploads and starts the app as often as wanted, no console, no FTP. And the part that matters more than the launch: libnx tells a netloader-launched app who started it (`__nxlink_host`), so `SdlSwitchAttachDebugChannel` (`switch_libnx.c`, called from `SdlBackendStartup` under `__SWITCH__`) points stderr at that host — and `OutputDebugStringA` mirrors every `DBG_*` line to stderr, so the debug log arrives on the PC *while the app runs*. Started from the menu instead, `__nxlink_host` is zero and nothing runs. Two traps: `podman` needs `--network host`, because hbmenu **connects back** to nxlink and with NAT it dials the host rather than the container; and `switch.h` cannot be included after `pilots_fwd.h` — `game_globals_struct.h` defines aliases for ordinary words (`#define offset`, `#define Format`) that rewrite libnx's own declarations, and the error lands inside the generated header, i.e. in the one file that must not be edited. That is why the nxlink code is its own translation unit with `<switch.h>` first.
- **The engine's file names and the original resources' names differ in case, on purpose.** The engine asks for `.\movies\intro.AVI`: the `movies` dir and the `intro`/`start` name come from the original's own data (`pConfigEx[1]`, and the script for the rest), while `.AVI`/`.BMP` come from the `aAvi`/`aBmp` data bytes — but the CD ships `MOVIES/INTRO.AVI`, all uppercase. Win9x ISO9660/FAT hid that mismatch, a case-sensitive FS does not, so on Linux **every** file entry point funnels through `WinShim_ResolvePath`/`ShimOpenWin` in `win32_shim.c` (`_open`, `CreateFileA`, `GetFileAttributesA`, `remove`, plus `mci_ffmpeg.c` before `avformat_open_input`): they walk the path component by component against the real directory. A new file open that bypasses those two functions silently breaks a verbatim copy of the original resources.
- Debug builds (`_DEBUG`) write `<exe name>_debug.log` next to the exe — `PILOT_RE_debug.log` for x86, `PILOT_RE_x64_debug.log` for x64 (`DbgLogInit` in `win32_shim.c` strips the exe extension), and on the Switch the target name is `PILOT_RE`, so the file there is `PILOT_RE_debug.log` — and also log to OutputDebugString (view with DebugView), plus a register/stack dump on crash. In release all `DBG_*` macros are no-ops (`debug_log.h`).
- **AVI goes through MCI, and `host.c` opens it the documented way.** `Host_AviOpen` fills an `MCI_ANIM_OPEN_PARMSA` (element path, `dwStyle = WS_CHILD`, `hWndParent = g_MainWindow`) and calls `mciSendCommandA` with `MCI_OPEN_ELEMENT | MCI_ANIM_OPEN_WS | MCI_ANIM_OPEN_PARENT`, then reads the child back with `MCI_DGV_STATUS_HWND` into `g_hAviWindow` and `MoveWindow`s it to the picture rect at size 0 (hidden until the first `WM_PAINT` places it). This matters because the sdl2 branch opened MCI by *writing past the end* of a 5-member `MCI_OPEN_PARMS` (`dwParam2[5]`/`dwParam2[6]`), which both misplaced the window by accident and tripped a fault inside `winmm.dll` on x64 that the branch then worked around with an SEH guard (`MciSendCommandGuarded`) plus a `mciSendStringA` fallback. **None of that exists here**: no guard, no fallback, and `clickskip.ps1` (which runs x64 by default) asserts the video opens, the `AVIWnd32` child exists and no exception is logged — so on the correct open the x64 dispatcher is fine. The other videos do not use MCI at all — `movie.c`'s `GmMovie_*` is the engine's own reader.
- **The child window and the game window share the skip path via `WM_PARENTNOTIFY`.** `Host_AviWndProc` (host.c) handles `WM_PARENTNOTIFY` for `WM_LBUTTONDOWN`/`WM_RBUTTONDOWN` and calls `Host_AviStopByMouse`; a click straight on the game window does the same through `WM_LBUTTONDOWN`/`WM_RBUTTONDOWN`, and Space/Return through `WM_CHAR` stop it via `MCI_STOP`. The child is **not** subclassed — mciavi32 runs its clicks through `DefWindowProc`, so the parent notification arrives on its own (the code says so in a comment; `clickskip.ps1` is what measured it).
- **After a video ends, only `MM_MCINOTIFY` gets the game moving again** — `Host_PlayAvi` waits in `do { … } while (g_AviPlaying)`, and the sole thing that clears that flag is `Host_AviWndProc` case `MM_MCINOTIFY`. That message is posted by mciavi32 to `MCI_PLAY_PARMS.dwCallback`, which the original fills as `dwParam2[0] = (unsigned __int16)g_MainWindow;`. That truncation is a Win9x assumption: an HWND fits in a word. On 32-bit Windows it is equally wrong today (0x601B6 → 0x1B6) but harmless, because 32-bit mciavi32 falls back to the AVI window's parent — and on x86 that parent is already the game window (the explicit `hWndParent` in `Host_AviOpen`). On x64 mciavi32 uses `dwCallback` directly, the truncated value names no window, `MM_MCINOTIFY` never arrives and the game **hangs on the last frame forever** — no exception, no log line, process still "Responding". So `Host_AviPlay` passes the whole `g_MainWindow` under `#if defined(_WIN64)` and keeps the original's truncation otherwise (`dwCallback` is `DWORD_PTR` on both arches). Symptom to recognise: the log simply stops after `PlayAvi: MCI device …` while the window keeps painting.
- **Fullscreen (`-fullscreen` at startup, Alt+Enter to toggle) is a port feature and a deliberate behaviour change**: the window goes `SDL_WINDOW_FULLSCREEN_DESKTOP` and the 640×480 picture is scaled to fit it (aspect kept, centred) via `s_PicX/Y/W/H` in `sdl_backend.c`; every mouse message goes through `SdlBackendClientToGame`, clicks on the letterbox are dropped (for the game that is exactly "the mouse left the window"), and the game itself keeps working in its own 640×480 space — windowed is the identity, so nothing changes without the flag. Three traps live here, all invisible to any log line about the *layout*:
  - **Windows: SDL only learns the window size from `WM_WINDOWPOSCHANGED`.** In SDL 2.30 that message is the *only* source (`SDL_windowsevents.c` handles it and never dereferences `lParam`; its `WM_SIZE` branch sends only RESTORED/MINIMIZED/MAXIMIZED, and `SDL_GetWindowSize` returns the cached `window->w/h`). The subclass used to route it to `MainWndProc` alone — the game repaints itself from it — so SDL's proc never ran: SDL's window stayed 640×480 in its bookkeeping, `IDXGISwapChain_ResizeBuffers` was never called, and the **swap chain kept its creation size 640×480 forever** while `SDL_GetRendererOutputSize` answered the live 1536×864. The picture was therefore drawn into a 640×480 backbuffer that DXGI stretched across the whole client (2.4× horizontally, 1.8× vertically) and cropped at the buffer edge — the fullscreen window showed a squashed, cut-off picture while `SdlUpdateLayout` logged perfectly correct numbers. **Fix: `SdlGameWndProc` now handles `WM_WINDOWPOSCHANGED` as its own case — `MainWndProc` first (game repaint), then `CallWindowProc(s_OrigWndProc, …)` so SDL gets it too**: `SDL_WINDOWEVENT_RESIZED` → `SDL_SendWindowEvent` (dedups when the size is unchanged) → `SDL_OnWindowResized` → `SIZE_CHANGED` → `D3D11_WindowEvent` → `IDXGISwapChain_ResizeBuffers`. No renderer recreation. `SdlDrawGameFrame` still resets the viewport to the whole output every frame (`SDL_RenderSetViewport(s_Renderer, NULL)`) as belt-and-braces and, in debug, logs `SdlDrawGameFrame: window … pixels … output … viewport … scale … logical … picture … tex …` — the viewport must equal the output. The game is DPI-unaware, so those numbers differ from the physical ones (client 1536×864 on a 1920×1080 screen) and `PrintWindow`'s bitmap is physical while its content is in the process's logical space — hence the harness accepting the bbox in either space.
  - **Windows: the movie child.** mciavi32 draws its `AVIWnd32` child 1:1 and cannot follow a scaled picture, so while a movie plays `SdlBackendSetNativeMovie(1)` drops the picture to its natural size keeping the centring offset (`s_NativeMovie`, `_WIN32` only), and `Host_RealignAviWindow` (`host.c`) moves the child to the picture rect on every layout change — the child lives in *window* pixels, hence `SdlBackendGameToClient`. It is a no-op until the child has been placed once (`g_AviWindowPlaced`, set by the first `WM_PAINT`); off Windows there is no child at all and `SdlBackendVideoFrame` draws the frame itself, following the layout every frame. The call is a port's own and not the engine's: it was carried over from the sdl2 branch, where it lived in `SdlUpdateLayout` and was lost in the move of MCI into `host.c` — the symptom was a movie left on the old client pixels in a corner while the backdrop BMP was already re-centred (measured on Alt+Enter during `start.AVI`).
  - **Linux/X11: SDL never resizes the window itself.** `SDL_SetWindowFullscreen(DESKTOP)` on X11 only sends `_NET_WM_STATE_FULLSCREEN` to a window manager and bumps SDL's own cache to the display bounds — with a bare Xvfb (every harness in `tests/linux`) the X window stays 640×480 at (320,120) while SDL reports 1280×720, and `SDL_SetWindowSize` is ignored once the flag is up. Proven with a standalone SDL probe containing no game code. `SdlApplyFullscreen` therefore **pre-resizes while still windowed** (`SDL_SetWindowPosition(0,0)` + `SDL_SetWindowSize(display bounds)`, mirrored on exit back to the game size, both `#ifndef _WIN32`), and `SdlBackendCreateWindow` passes `px=py=0` under `-fullscreen`, because SDL defers `SetWindowPosition` for a hidden window and never replays it once the fullscreen flag is up.
- **Ctrl held marks the interactive objects (port feature, debug aid, `hotspots.ps1`/`hotspots.sh`)**: white discs over every object the engine's own click hit test would accept — nothing is marked otherwise. `SdlUpdateHotspots` (called once per pump from `SdlBackendPumpEvents`, one site for both OSes) reads the key with `GetAsyncKeyState(VK_CONTROL)`, which is the *only* keyboard call that answers the same way on both platforms: a real user32 on Windows, a `SDL_GetModState` shim on Linux (`win32_shim.c`). That asymmetry is the point — on Windows the wndproc subclass hands `WM_KEYDOWN` straight to `MainWndProc` and SDL never updates its own modifier state, so `SDL_GetModState()` would be dead there, while polling a posted message never changes the *physical* state `GetAsyncKeyState` reports (hence the harnesses use real `keybd_event`/XTEST, not `PostMessage`). The console's **R held** is the same overlay's second held source: `SdlPollSwitchControls` sets `s_PadOverlayHeld`, `SdlUpdateHotspots` ORs it into the Ctrl state (one pump of lag, a millisecond — the pad poll runs after it); on every other platform the flag simply never sets. Ctrl was picked over Shift (already a game modifier: `main.c` adds 8 to `keyIndex`) and Alt (already Alt+Enter, and a window manager may eat it first). `SdlCollectHotspots` walks `g_RenderObjectsStart → g_RenderObjectsEnd` the way `ProcessInputAndRender` does — **this is the first time the port layer reads game globals, and it is read-only**: composites `(flags & 3) == 3`, sprite channel type 2 or 3 (`LOBYTE(g_SpriteSlotArray[slot].baseData)`), the pixel position is on the *child* (a composite's `posX`/`posY` are child indexes, `0xFFFF` = none) and the size is the first two `u16` of the sprite header reached through the 32-bit pointer slot, exactly as `CheckObjectHitTest` reads it. Two traps on the drawing side: the discs are drawn in **window** client px (one radius for X and Y — in fullscreen `s_PicW`/`s_PicH` scale differently and a game-space radius comes out an ellipse) and the state edge **forces a present** (`SdlPresentCurrent`), because on a resting screen nothing else would ever redraw and the markers would either never appear or never go away. Measured: 18 objects on the startup screen, 14 in scene 1, and `x86check.ps1` still passes — the walk never writes, so the game cannot tell it ran.
- **A movie's sound is the port's own, and it exists only through the mixer.** The shipped AVIs carry a second stream (`hdrl/LIST strl` with `strh.fccType 'auds'` and a 16-byte `strf` WAVEFORMATEX — PCM, mono, 8 bit; 22050 Hz in INTRO, 11025 in START and FINAL, samples as `01wb` chunks in `movi`), but **ffmpeg's avi demuxer shows no audio stream for these files at all** (`non-interleaved AVI`, one stream), the game's own AVI reader never had sound, and there is no mciavi32 on Linux or the Switch to be asked. So `mci_ffmpeg.c` walks the RIFF by hand on a second `FILE*` (`MciAudioProbe`) and counts the same 776062 / 554989 bytes the stream's own `dwLength` promises, then feeds `SdlMix_MovieOpen`/`Write`/`Close` — a **third ring** in `sdl_backend.c`, so skipping a movie drops its queued sound without touching the music or a blip in progress. Pacing is the video's clock, and it is a *stream* clock (`last_end_us - base_wall_us`), so a starved pump holds the sound with the picture instead of running it ahead; a gap over half a second is dropped rather than hurried through, because catch-up would sound like a fast-forward. Sharing one device is therefore the **default on every non-Windows platform** (`SdlShareAudioWanted`; Windows keeps the two devices because there mciavi32 plays the movie's own sound), and `PILOTS_SHARE_AUDIO=0/1` forces either way — which is how the shared path gets measured where a speaker can be replaced by a number: the mixer logs, once per 5 s of audio, the frames **and the peak** each source contributed. That peak is load-bearing: the wave path's first shared version started its conversion from `int v = 128` instead of `src[i]`, so it queued 73728 frames per 5 s of pure zero — counted activity, inaudible result, and only the peak said so. Two measured facts to keep honest: the movies' rates are exact integer ratios into the mixer's 44100 (×2 and ×4), and INTRO's track is 35.2 s against a 34.0 s picture with its last ~4 s *silent* (no sample differs from 128), which is why a run reporting `749625 of 776062 bytes reached the mixer` is correct. Covered by `tests/linux/movieaudio.sh`.
- **Two more port features in the picture path: `-` toggles stretched ↔ aspect-kept, and a load now says so.** `-` (`VK_OEM_MINUS` = **0xBD**, not 0xBE — 0xBE is the period key, and the harness's first version posted that and silently tested nothing until the game answered with `WM_CHAR wp=0x2E`; the port's own scancode table at `SDL_SCANCODE_MINUS` had it right all along) is swallowed before the game sees it, on both paths: the Windows subclass's `WM_KEYDOWN` case and the SDL event pump. Because "stretched over the whole screen" only means something in fullscreen, the first press from a window goes fullscreen **and** stretched (`SdlBackendToggleStretch` sets `s_StretchPic`, and `SdlUpdateLayout`'s stretch branch hands the picture the whole client); after that the key only flips the stretch, and Alt+Enter is still the way back to the window. Without the key nothing changes, which is what `x86check.ps1` and `fullscreen.ps1` keep asserting; `tests/windows/stretch.ps1` presses it three times and reads the rects back out of `SdlUpdateLayout` (stretched == client at (0,0); own aspect == exact 4:3, centred, x > 0). **On the console the same toggle is the Joy-Con `-` button** (`SWITCH_PAD_MINUS`, from `HidNpadButton_Minus` in `SdlSwitchPollPad`, checked on the press edge only, and it goes to `SdlBackendToggleStretch` directly - not to the game, which has no binding for it; there is no harness for this one, `stretch.ps1` covers the Windows half of the same function). What makes it possible at all on that platform is worth keeping: the shipped `switch-sdl2` has **no `SWITCH_SetWindowFullscreen`**, so SDL's fullscreen there is nothing but its own cache - but its `SWITCH_SetWindowSize` is real, it calls `nwindowSetDimensions(nwindowGetDefault(), w, h)` and recreates the EGL surface, which is the console's framebuffer. So the pre-resize `SdlApplyFullscreen` does `#ifndef _WIN32` (added for bare Xvfb) is not belt-and-braces on the Switch, it is the only mechanism, and it is what turns the panel-scale of a 640x480 framebuffer into a framebuffer that equals the panel - after which the port's own `s_PicW`/`s_PicH` decide whether the picture keeps 4:3 or fills it. **A load is now visible**: a scene loads inside the game's own loop - seconds of reading with nothing drawn, which reads as a hang - and the port cannot wrap that loop, so `_read` in `win32_shim.c` beats `SdlBackendLoadBeat`: one second of a still screen (`PILOTS_LOAD_QUIET_MS` overrides) *with bytes moving* is a load - the still screen alone is not, since a resting screen is still and simply does not read. The indicator is a procedural ring of marks at the bottom of the picture, not the app icon, on purpose: the `.ico` is carved out of `PILOTS.EXE` and is only where the game data is. Two things the first version got wrong, both now measured: the clock a load is measured on has to be **the last rect the game blitted** (`s_LastGameBlit`, set only in `SdlBackendPresentRect`), not the last present — a layout change or the spinner's own repaint shows a frame too, and either one restarting the clock froze the mark after a single step and emptied its byte count, which is how a real 40 s font load came out as `the screen stood still 40 s with 0 KB read`; and the mark is only drawn while the reads are *fresh* (`SDL_LOAD_ACTIVE_MS`), because spinning while nothing is being read would claim activity the port cannot see — a hang is a different thing from a load, and the summary says which it looked like (`the reads stopped N ms before the picture moved again`). Shim platforms only (Linux, Switch) - on Windows `_read` comes straight from the CRT, so there is nothing to beat.
- **The engine repaints its pointer only from a mouse message, and on the console nothing else draws it (port feature: `SdlCursorKeepAlive`)**. On Windows and X11 the game's arrow is invisible-by-design: a real system cursor is composed over the window. The Switch has none at all (`nm` finds no `ShowCursor` in the shipped video driver), so there the arrow is only ever what the game last painted, and anything the scene paints over that spot takes it away until the player moves - the reported symptom, Switch-only. What the port calls is the engine's own `AddObjectToDirtyRegions(&g_CursorObject)` (`#ifdef __SWITCH__`), which is exactly what `HandleGameEvent` calls when the pointer moves, so the arrow returns through the dirty-region pass in the same frame the pump is in - nothing moves, so nothing has to be restored. Three tries and three measurements stand behind that sentence. (1) The same call, made too early: on the first console run no mouse message had arrived yet, the object was parked at `(0,0)`, and the repair drew the arrow into a corner nobody looks at - which read as "this object is not the arrow", and the log later showed it at `(320,240)` following the first touch, so it *is* the arrow. (2) `WM_MOUSEMOVE` one pixel away and back: it does bring the arrow back, but a move also makes the engine restore what it believes was under the old position, and over an animated scene that restore is not faithful - asked to do it every frame, the port made the player watch that smudge flicker, reported as "the cursor blinks *faster* than before". (3) Deciding "the arrow was overpainted" by counting rects blitted since it was last seen: the arrow's own repair is itself a blit, so at threshold 16 with a 500 ms re-arm the repair fed itself into a metronome - the log shows it at an exact half-second rhythm with **30-34 rects**, which is an arrow, not a scene, and the player saw the cursor **blink in time**. The check is now made on the picture: the port keeps a 65x65 square of its own shadow frame (`s_CursorSnap`, the frame the game itself last drew - the same memory the texture is uploaded from) centred on `g_VideoConfig.cursorX/Y`, and asks for a redraw only while that square actually changes (`CURSOR_DIFF_MIN` = 8 px). A resting scene changes nowhere → nothing is sent; an animated one changes every frame → the arrow is asked back every frame, and every shown frame contains it, which is why this form cannot blink the way the timer did. The snapshot is deliberately **not** refreshed on a mismatch but one pump later - the frame the repair produced; refreshing it from the erased frame is the same self-feeding trap the rect counter fell into.
- **The level map's cursor keeps the pointing hand after the pointer leaves a level flag — original behaviour, do not "fix" it** (confirmed against the 1996 original by the player, 18.10.2026). The shape is a font glyph: `InitGraphicsMode` puts `g_FontSlotArray[g_CurrentFontIndex]` into `g_CursorObject` (arrow = font 0, the hand = font 1), the script switches it with `Native_InitGraphicsWithFont`/`Native_InitGraphicsDefault`, and the engine's only revert (`g_CursorObject.flags & 4` → `InitGraphicsMode(1,0)`, render.c:764) never fires either. A dedicated probe measured the whole round trip on Windows x64 and the Switch alike: entering a flag changes `font` 0→1, leaving changes nothing (`font` stuck at 1, `fl` never gains bit 4) — the script's leave-branch does not run on any platform, exactly as in the original. The probe, its repair log line and the `outside picture` line were removed together with the closed question (`tests/windows/hover.ps1`, which drove the decisive 220-move hover sweep, is gone too); on the console the hourglass during animations is the engine's multi-frame cursor working as designed.
- **What a click is to this engine, and why the console's R is the overlay.** `ProcessInputAndRender` folds the frame's mouse event into one byte and, for the clickable composites, takes the event only when that byte is **exactly 144 or 160** (`render.c`: `v14 != 144 && v14 != 160`) - the release of the left or right button with nothing else in it; the coordinates that decide which object it belongs to are the **cursor's**, not the click's (only the idle event code swaps the click's in). `keyIndex` (main.c's arrow/action keys) never becomes navigation on its own: it goes to text input and, when set, ADDs to that byte (`v14 |= inputFlag | 0x40`) - so a key in the same frame as a click makes the object **refuse** it. This is what killed the old walk scheme: the port walked the clickable list on a press and clicked there (`SdlWalkHotspots`), and the console measured where such a walk lands - `(607,450)`, the level map's **exit button** (the run went on to the next screen from there), and `(552,448)` on the startup screen, which quit the game through the script's own loop-stop byte. "Switch the pilots" was abandoned on that evidence and the whole walk/click/post-key machinery deleted with it. What remains: **R held** is the interactive-object overlay, the same discs Ctrl gives - `SdlPollSwitchControls` sets `s_PadOverlayHeld`, which `SdlUpdateHotspots` reads as a second held source next to `GetAsyncKeyState` (one pump of lag, a millisecond), and `SdlDumpHotspots` prints the clickable list with coordinates on the R press edge, which is what turns "the second one from the left" into numbers (the character screen's panel row is (31,450), (95,448), (223,448), (607,450)).
- **What a deploy does to the console's log, and what its three closing lines mean.** `scripts/deploy_switch.sh` uploads the `.nro`, then *downloads* the previous `PILOT_RE_debug.log` into `/tmp/pilots_deploy_logs/` and deletes it on the SD, so the next run starts from an empty file — which means **two deploys in a row leave no log at all**, and that is not a fault. The vocabulary is deliberately three-valued because a two-valued one caused a wrong diagnosis: `LOG_ARCHIVED (path)` + `LOG_DELETED` is the normal pair; `LOG_ABSENT` means there was nothing to archive (no run since the last took it — the curl above, note, returns a *successful empty body* for a missing path, hence the `-s` test rather than an exit code); and `LOG_DELETE_FAILED` now fires **only** when the file was just read and still refused to go, i.e. a process holds it open — the game is running, and since the `.nro` on the card was already overwritten, the running process is the *old image* and must be closed before the new one is started. Reading the old catch-all wording as "held open" once led to claiming the console was mid-run when it was simply idle.
- **The port's message queue merges mouse moves, because Windows does** (`PostMessageA` in `win32_shim.c`): a not-yet-dispatched `WM_MOUSEMOVE` for the same window is **overwritten**, not queued behind its predecessor, which is what Win32 documents (a `WM_MOUSEMOVE` is discarded when another one is already in the queue) and what SDL's own pump does to `SDL_MOUSEMOTION`. Without it a device that reports often — the console's analog stick posts a move on every poll it is held aside — fills the queue with a trail of positions the game replays one by one, each an erase, a redraw and a present, and what the player sees is **the scene's animation stopping while the pointer moves** (reported as bug #2; putting this in the shim rather than in the pad layer is deliberate, because a fast mouse on any shimmed platform floods the same queue). Windows is untouched: there `PostMessageA` is user32 and the OS already coalesces, and `win32_shim.c` is not even in that build — which is how the mistake of reaching for `WinShim_MsgDispatched`/`WinShim_MsgQueueDepth` unconditionally came back as a **link** error only on Windows (`SdlProfMsgDispatched`/`SdlProfQueueDepth` are the shims that answer 0/-1 there, because the queue is not the port's to measure). `SdlLoopProfileTick`, called from both pumps, prints one line per two seconds (`pumps … messages taken … presents … us in present … rects (msg/frame split) … frames/s … frame N ms ago (delay M) … queue now`) because "the animation froze" has at least three causes that look identical from the sofa; the first Linux measurement already cost nothing to learn: ~60 pumps/s at rest with **0 presents in 2 s**, and a present averaging ~10 ms. The msg/frame split attributes a rect to the message path (the cursor, rendered inside the dispatch — the flag wraps both dispatch loops) or to the frame path (the scene); `frames/s` counts the shim's `GetCursorPos`, which main.c polls once per frame; `frame N ms ago` is main.c's own pacing read back (`frameDelayMs + g_LastFrameTime < now`), so a healthy loop keeps N at about M and a starved one lets it grow while pumps keep coming.
- **The console's stick→cursor stream is the engine's own `WM_MOUSEMOVE` path, throttled to 50 ms — and both halves of that sentence are measured** (`SdlPollSwitchControls`, `sdl_backend.c`): every posted move makes the wndproc run `UpdateCursorPosition → RenderDirtyRegions` *synchronously*, so the stream's rate is simultaneously the cursor's repaint rate and a tax on the scene's frame budget. Three states were played on the console, each with its number. (1) **Unthrottled** (one move per pump while the stick is held): 343-650 msgs/s — the frame *starved* first (frames 1-2/s, frame age 1388 ms, each message blocking ~10 ms in `SDL_RenderPresent`), then the present deferral `s_InMsgDispatch` (message-path rects blit only; the show is the pump's `SdlFlushPresent`, the flag wraps both dispatch loops) fixed the starvation (frame age back to 76-147 ms, healthy loop) but **not the picture**: at that rate the pass's snapshot restore (`CopyRectToBackbuffer` from `g_SnapshotBasePtr`) painted over what the scene had just animated, so the walking character still *appeared* frozen while the profile looked fine — "the animation froze" has these two causes and they need different fixes, which is exactly why `SdlLoopProfileTick` splits msg/frame rects. (2) **No stream at all** (the pad wrote `g_VideoConfig.cursorX/Y` directly, no messages): the walk and the sound were fine, but the **cursor broke** — invisible on the level-select map, appearing only while moving and vanishing again in the scenes. Reason: the frame-end `HandleGameEvent` repaints the cursor object only while `g_InputState[1]` is set (render.c:767/773/871), and the writers of that bit are `=0` at scene init, `= inputState` per frame from main.c's pointer-inside-the-picture test, and `=1` **only** in `UpdateCursorPosition` — the per-message path such a change deletes; with it gone the arrow's painting hung entirely on one bounds check, and measured it did not hold everywhere. (3) **The shipped state: the stream restored and throttled** (`MOVE_MIN_INTERVAL_MS` 50 ms, one message at the *current* position — never a backlog — plus a pending flag so the final position within one interval of the stick letting go): a real mouse's report rate, ~20 sync passes/s ≈ 6% of a second's CPU against the old 343-650, cursor and walk both alive, `WM_SETCURSOR` still ahead of each move the way a real mouse arrives. Clicks (`SdlPostClick`) still post unthrottled — they re-post `WM_MOUSEMOVE` at the aimed position first, so a click always lands where the player pointed even if the throttle has not flushed yet. If the cursor ever regresses again, start at `SdlBackendClientToGame`: a mapped point outside the picture is what main.c reads as `inputState=0` ("erase the cursor, do not repaint") - the letterbox drops are by design, anything else is the failure link (the capped-40 line that used to say this with numbers went with the closed cursor investigation).
- **What the mixer hands the speakers can now be looked at, not inferred** (`SdlMix_Dump`, debug builds): the first 6 s of the mixer's own output are recorded verbatim and written as `pilots_mix.wav` next to the exe, armed by the first window that carries a **game effect** (not the movie — the movie path was verified this way and needs no re-proving). It exists because every summary the mixer already logs is a statistic of the same buffer the device receives: `out peak 8224` is printed identically for a real sound and for a DC offset, and only the shape tells them apart. The file is pulled with `scripts/deploy_switch.sh --pull-dump` (the console has no command line and no environment, so unlike Linux/Windows, where the recorder is `PILOTS_AUDIO_DUMP=1`, on the console it is always armed). Writing it from the audio callback would be wrong, so a full recorder is emptied by the next pump — and one attempt only, guarded by `s_MixDumpDone`: the first version let the callback re-arm a recorder whose buffer had already been freed, the second `CreateFileA(CREATE_ALWAYS)` truncated the good file to its 44-byte header, and the log cheerfully reported two successful writes. Verified locally on Linux with `SDL_AUDIODRIVER=dummy` (the dummy driver still runs the callback in real time): 264600 frames, peak 19789, the first ~4 s silent and real 53–86 Hz content after that, which is INTRO's own audio, so the recorder and the movie path are both honest. Note the path is built Windows-shaped (`\home\…\pilots_mix.wav` in the log) and still lands next to the exe, because `CreateFileA` goes through the shim's own resolution — a "fix" that appends a separator of the port's own doubles it and breaks the write.
- **`deploy_switch.sh` refuses to upload an old `.nro`** (`STALE_NRO`, bypass with `PILOTS_DEPLOY_FORCE=1`): it compares the `.nro` against newer `SRC/*.c|h`. This is not a nicety — a Switch build failed on a compile error, the previous `.nro` was still in the build dir, and the deploy reported `UPLOAD_OK` for it, so the console ran a build without the fix whose behaviour was then read off its log. A stale binary is a different experiment, not a slower one.

- **MIDI synth flavor**: emulator + bank are picked in `SdlMidi_Open` (`sdl_backend.c`) — `SDL_MIDI_BANK` selects one of the 79 embedded banks (`adl_getBankNames()`), the current choice is 68 (GM set by J.A. Nguyen & Wohlstand); `emu=Nuked OPL3` is the default. libADLMIDI is LGPLv2.1+/GPLv3+ (`third_party/libADLMIDI/LICENSE*`) — keep that in mind for redistribution.
- Two MIDI log lines look like arch invariants but are **not** — they are 10 ms-timer timing: `SdlMidi_Pump: first audible PCM (X of 1024 samples nonzero)` (937 vs 941, and the same x86 build produces both across runs) and `SdlMidi_Reset: N messages processed` (x86 logs one, x64 two, but the reset *sequence* is identical — only whether a timer tick lands inside a short Stop/Start gap). Both are commented as such in `sdl_backend.c`; see `tests/README.md` for the measurements and the `audio.ps1 -Arch x86|x64` comparison run.

## Code conventions that matter

- Every `.c` file includes exactly one header: `pilots_fwd.h` (the umbrella: `defs.h` IDA compat types like `_BYTE`/`LOBYTE`/`SBYTE2`, `pilots_types.h`, `debug_log.h`, `game_globals_struct.h`, `pilots_globals.h`). New globals/functions go through `pilots_globals.h`. The only exception is `sdl_backend.c`, which additionally includes `<SDL_syswm.h>` and `"adlmidi.h"`.
- `game_globals_struct.h` and `game_globals_init.h` are generated (`/* Auto-generated by gen_globals.py - DO NOT EDIT */`) and must match the original EXE's data section byte-for-byte. `gen_globals.py` is **not in the repo** — don't hand-edit these or "fix" field order/layout.
- Decompiler style is intentional: original names (`v5`, `a1`, `dword_41022C`), packed structs, stack-overlay comments (e.g. `resource.c` `LoadDataFile`). Don't rename, reorder, or idiomatic-rewrite — behavior must stay faithful to the original binary; comments explaining odd code are load-bearing.
- Alias macros in `pilots_fwd.h` (e.g. `g_MaxReadBufferSize` → `MaxCharCount`, `unk_41020C` → `g_Globals._trail_…`) keep old and generated field names working — check there before renaming anything global.
