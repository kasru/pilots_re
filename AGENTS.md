# AGENTS.md

## What this repo is

Byte-faithful C reconstruction of the engine from the 1996 game «Братья Пилоты», decompiled from the original `PILOTS.EXE` (IDA Hex-Rays). All game logic lives in bytecode scripts inside the original game's data file — the C code is just the interpreter/player.

- All sources are flat in `SRC/` (no subdirs, no packages).
- Docs are in Russian: `SRC/docs/README.md` → per-subsystem pages (`architecture.md`, `scripting.md`, …). Trust code over docs when they disagree. They predate the SDL2 port — window/present/audio specifics live in `SRC/sdl_backend.c`.
- SDL2 port: window, input, present and PCM sound effects go through SDL2 (`SRC/sdl_backend.c` subclasses SDL's wndproc so the game's `MainWndProc`/`VideoWndProc` still see raw Win32 messages). MIDI music renders through **libADLMIDI** (OPL3 emulation, submodule `third_party/libADLMIDI`) into its own SDL queue-audio device (`SdlMidi_*` in `sdl_backend.c`) — only the winmm 10 ms event timer (`timeSetEvent`) survives from the old midiOut path. AVI video stays on MCI.

## Build (the only automated verification — there are no unit tests, linter, or CI)

- Four bats, each `pushd`ing to its own dir so they work from any CWD:
  - x86 (the proven baseline): `SRC\build_sdl_debug.bat`, `SRC\build_sdl_release.bat` → `SRC\PILOT_RV.EXE` (+ `.pdb`, `.map`).
  - x64 (the LP64 milestone toward the Switch/aarch64 build): `SRC\build_sdl_x64_debug.bat`, `SRC\build_sdl_x64.bat` → `SRC\PILOT_RV_x64.EXE` (+ `.pdb`, `.map`). Separate name so it can sit next to the x86 build; no `/FIXED` because the x64 image keeps its base relocs.
  - The exe must never be named `PILOTS.EXE`: the engine opens its data file as `.\PILOTS.EXE` (CWD-relative), so a rebuilt exe named `PILOTS.EXE` would read *itself* as game data — and it must never be copied over the original game's `PILOTS.EXE` (that file holds the resources). Run the exe from a directory containing the original game data.
  - `SDL2.dll` is copied next to the exe, but both arches import the same `SDL2.dll` name, so only the last-built flavor can actually run — rebuild the arch you want before running it.
- Intermediate `.obj` files go to repo-root `build\<Configuration>\<Platform>` — one dir per bat, so all four builds coexist and never stomp each other: `build\Debug\x86`, `build\Release\x86`, `build\Debug\x64`, `build\Release\x64`. The debug bats also drop their `/Fd` compiler PDB there; the release bats pass no `/Zi`, so they have none. `SRC\` keeps only runtime + linker outputs: the exe, `SDL2.dll`, the linker `.pdb`/`.map`/`.ilk`, and the game data.
- Toolchain paths are hardcoded at the top of each bat: VS 2022 Community MSVC `14.44.35207`, Windows SDK `10.0.26100.0` (x86 bats use `Hostx86\x86`, x64 bats `Hostx64\x64`). Edit `VCTOOLS` / `WINSDK` / `SDKVER` there if your install differs — don't switch to `vcvarsall`/CMake. SDL2 headers/libs come from `third_party\SDL2` (include/, plus lib/x86/ or lib/x64/) — edit `set SDL2=` if it moves.
- Source files are listed explicitly in each bat. **Adding a `.c` file requires editing all four bats.** The same applies to libADLMIDI: each bat has its own compile blocks (C++ core with `/TP`, C parts with `/TC`, the `ADLMIDI_OPTS` feature defines) — if the submodule update changes its source set or options, change **all four** bats the same way. `SRC\test_cast.c` and `SRC\test_wave.c` are scratch files deliberately left out of the build (`test_wave.c` is a standalone audio-harness with its own `main()`, built ad-hoc; it links the libADLMIDI objs too, so build them first).
- Compiles with `/W3` but many warnings are suppressed and `/WX-` — warnings never fail the build; only errors do.
- `.gitignore` covers build droppings (`*.obj`, `*.exe`, `*.pdb`, `*.map`, `*.ilk`, `*.dll`, `*_debug.log`), the whole `build/` dir, plus `*.SAV` — don't force-add them.

## Tests (manual harnesses, driven by scripts — still no unit tests, linter, or CI)

Everything for verifying a change lives in `tests/`, split by OS; `scripts/` now holds only `run_podman.sh` (the Linux launch helper). `tests/README.md` has the full per-script table — read it before touching a harness. Highlights:

- **Run them with PowerShell 7, from a file:** `& "$env:ProgramFiles\PowerShell\7\pwsh.exe" -NoProfile -File tests\windows\<name>.ps1`. Never `pwsh -Command`, never the `pwsh` on PATH — that is PS 5.1 (no ternary, no `[UIntPtr]`, mangles embedded quotes, `Set-Content -Encoding utf8` writes a BOM).
- Harnesses resolve `SRC` from their own location (`$PSScriptRoot\..\..`), so any checkout path works.
- `buildall.ps1` — all four bats back to back, prints SUCCESS/FAILED only. `x86check.ps1` — builds x86 debug **last** (both arches share `SDL2.dll`, so only the last-built arch runs), plays 12 s and asserts the baseline markers `auxMainLoop: startResourceId=1`, `ENTER: GameMainLoop` ×2, zero `EXCEPTION: 0xC000` — this is how a 64-bit/LP64 change gets proven to leave 32-bit behaviour identical.
- `audio.ps1` drives the music/sound panel buttons and asserts they alternate; `-Arch x86|x64` runs the *same* click script on either build (default x64), which is the only honest way to compare the two — several MIDI log values look arch-specific but are timing. `rundir.ps1` supplies the scratch run dir and the startup-dialog detector (below).
- **A wrong-arch `SDL2.dll` does not crash, it blocks.** The exe fails to load before `main()`, so there is no window and no log, and Windows shows a modal "Ошибка при запуске приложения (0xc000007b)" — which reads as "приложение падает". Two traps make it hard to automate: the box is owned by a **different** pid (not the game's, so filtering by `$p.Id` misses it and `MainWindowHandle` stays 0), and `MainWindowHandle` can also return the dialog itself, in which case the harness "clicks" it and reports a phantom crash. `rundir.ps1` therefore matches `#32770` windows on `<exe>.EXE` in the *title* (`PILOT_RV` is a substring of `PILOT_RV_x64`, so a bare process-name match grabs the other arch's leftover box), collects the Static children's text (the code is in the body, not the title) and clicks the button; `New-GameRunDir` clears leftovers from earlier runs first.
- `pfuzz.ps1` is the workhorse: starts x64 debug, walks into scene 1, sprays clicks + keystrokes, screenshots, greps the debug log for `EXCEPTION: 0xC000`. `relfuzz.ps1` is the same against release. `play.ps1` dwells 4 s per click so animations/dialogue can settle; `realfuzz.ps1` uses real `SetCursorPos`+`mouse_event` input. `probe.ps1` = rebuild x64 debug + `pfuzz` in one go.
- **Clicking, not driving the real cursor.** Logical 640×480 coords; `PostMessage(hwnd, 0x0200,0,LP)` → `0x0201,wp=1` → `0x0202,wp=0` with `LP(x,y) = ((uint)y<<16)|((uint)x&0xFFFF)`. It needs no focus and moves no cursor, whereas real input goes to whatever window is under the pointer and Windows refuses `SetForegroundWindow` from a background process — hence "clicks land in another window". Confirm delivery by the game's own line `SdlGameWndProc: msg=0x201 wp=0x1 lp=…`. `SetCursorPos` needs **physical** coords = logical × 1.25 (the process is DPI-aware, the game window is not).
- **Reproduce crashes on a debug build only** — in release `DBG_*` are no-ops (`debug_log.h`), so a release crash logs neither the exception nor the register dump.
- `check_x64_file.bat` compiles one `.c` at a time under x64 and lets the pointer-mismatch warnings through (they are the signal); `analyze_probe*.ps1` histogram the resulting `C4xxx` logs.
- Linux side: `tests/linux/*.sh` `cd "$(dirname "$0")/../.."` (nothing is hardcoded to `/home/ntadmin/...` any more) and need `x11ctl.py` — an X11/EWMH driver over ctypes+libX11, standing in for xdotool/wmctrl, which the host does not have.

## Runtime gotchas

- Needs the original game files: `main.c` hardcodes the data path to `.\PILOTS.EXE`, resolved against the **process CWD**. Run `PILOT_RV.EXE` from a directory containing the original `PILOTS.EXE`; video `.avi`/`.bmp` lookup is also relative to that path.
- Debug builds (`_DEBUG`) write `<exe name>_debug.log` next to the exe — `PILOT_RV_debug.log` for x86, `PILOT_RV_x64_debug.log` for x64 (`DbgLogInit` in `win32_shim.c` strips the exe extension) — and also log to OutputDebugString (view with DebugView), plus a register/stack dump on crash. In release all `DBG_*` macros are no-ops (`debug_log.h`).
- AVI video on **64-bit Windows is broken in the OS, not in the port**: `mciSendCommandA(MCI_OPEN)` does not return an error, it faults inside `winmm.dll` (WER names `WINMM.dll` as the faulting module, offset `0x176fa`), killing the process the moment a real `.AVI` is passed as the element. `mciavi32.dll` and the `msrle32.dll` RLE codec are both on disk — it is the 64-bit MCI dispatcher itself that is broken. A 32-bit build plays the very same file through SysWOW64 fine. No error code ever comes back, so `video.c` routes every `mciSendCommandA` through `MciSendCommandGuarded` (SEH) which catches the fault and latches it in `s_MciFaulted`; a non-existent file fails cleanly and never reaches the driver. **On `_WIN64` only**, `OpenMCIVideoDevice` then falls back to the *string* API — `mciSendStringA("open <file> type avivideo …")` never trips the broken dispatcher, so `OpenMCIByString` gets a device id and the intro actually plays. The other videos do not use MCI at all — `ProcessVideoCommands` is the engine's own AVI reader.
- **Where the intro lands in the window differs between the arches by accident.** The decompiled `OpenMCIVideoDevice` does `dwParam2[5] = 0x40000000; dwParam2[6] = (DWORD_PTR)g_MainWindow;` past the end of the 5-member `MCI_OPEN_PARMS`. On x86 `DWORD_PTR` is 4 bytes, so those stores happen to land on `_mciWndParms.dwCallback/.hWnd`, and that `hWnd` is what makes mciavi32 create `AVIWnd32` as a `WS_CHILD` of the game window. On x64 `DWORD_PTR` is 8 bytes, the stores fall past the struct, `hWnd` stays uninitialized and the video opens as a separate top-level window. A probe (`build/probe_wnd.c`) confirmed mciavi32 on x64 ignores every parent hint passed through MCI itself (`MCI_OWN_WINDOW`+`hWnd`, +`dwCallback`, `MCI_ANIM_WINDOW_HWND`, both, and post-play — all give the identical top-level `AVIWnd32` with `WS_CHILD` never set). So the `_WIN64` block in `video.c` assigns `v5`/`hWnd` explicitly and then strips the popup style, adds `WS_CHILD|WS_CLIPSIBLINGS` and `SetParent`s the window under `g_MainWindow` right after `MCI_WINDOW`. Video is deliberately **not** stretched on either arch: the original plays 320×240 at client (160,120) over the background BMP.
- **After a video ends, only `MM_MCINOTIFY` gets the game moving again** — `PlayIntroVideo` busy-waits on `while (g_VideoPlaying)`, and the sole thing that clears that flag is `VideoWndProc` case `0x3B9`. That message is posted by mciavi32 to `MCI_PLAY_PARMS.dwCallback`, which the original fills as `dwParam2[0] = (unsigned __int16)g_MainWindow;`. That truncation is a Win9x assumption: an HWND fits in a word. On 32-bit Windows it is equally wrong today (0x601B6 → 0x1B6) but harmless, because 32-bit mciavi32 falls back to the AVI window's parent — and on x86 that parent is already the game window (the `DWORD_PTR` accident above). On x64 mciavi32 uses `dwCallback` directly, the truncated value names no window, `MM_MCINOTIFY` never arrives and the game **hangs on the last frame forever** — no exception, no log line, process still "Responding". So `_WIN64` overrides it with the whole `g_MainWindow` (`dwCallback` is `DWORD_PTR` on both arches). Symptom to recognise: the log simply stops after `PlayIntroVideo: g_MCIDeviceID=N` while the window keeps painting.
- MIDI synth flavor: emulator + bank are picked in `SdlMidi_Open` (`sdl_backend.c`) — `SDL_MIDI_BANK` selects one of the 79 embedded banks (`adl_getBankNames()`), the current choice is 68 (GM set by J.A. Nguyen & Wohlstand); `emu=Nuked OPL3` is the default. libADLMIDI is LGPLv2.1+/GPLv3+ (`third_party/libADLMIDI/LICENSE*`) — keep that in mind for redistribution.
- Two MIDI log lines look like arch invariants but are **not** — they are 10 ms-timer timing: `SdlMidi_Pump: first audible PCM (X of 1024 samples nonzero)` (937 vs 941, and the same x86 build produces both across runs) and `SdlMidi_Reset: N messages processed` (x86 logs one, x64 two, but the reset *sequence* is identical — only whether a timer tick lands inside a short Stop/Start gap). Both are commented as such in `sdl_backend.c`; see `tests/README.md` for the measurements and the `audio.ps1 -Arch x86|x64` comparison run.

## Code conventions that matter

- Every `.c` file includes exactly one header: `pilots_fwd.h` (the umbrella: `defs.h` IDA compat types like `_BYTE`/`LOBYTE`/`SBYTE2`, `pilots_types.h`, `debug_log.h`, `game_globals_struct.h`, `pilots_globals.h`). New globals/functions go through `pilots_globals.h`. The only exception is `sdl_backend.c`, which additionally includes `<SDL_syswm.h>` and `"adlmidi.h"`.
- `game_globals_struct.h` and `game_globals_init.h` are generated (`/* Auto-generated by gen_globals.py - DO NOT EDIT */`) and must match the original EXE's data section byte-for-byte. `gen_globals.py` is **not in the repo** — don't hand-edit these or "fix" field order/layout.
- Decompiler style is intentional: original names (`v5`, `a1`, `dword_41022C`), packed structs, stack-overlay comments (e.g. `resource.c` `LoadDataFile`). Don't rename, reorder, or idiomatic-rewrite — behavior must stay faithful to the original binary; comments explaining odd code are load-bearing.
- Alias macros in `pilots_fwd.h` (e.g. `g_MaxReadBufferSize` → `MaxCharCount`, `unk_41020C` → `g_Globals._trail_…`) keep old and generated field names working — check there before renaming anything global.
